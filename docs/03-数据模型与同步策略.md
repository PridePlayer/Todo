# 03 · 数据模型与同步策略

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0（第一批交付） |
| 数据库 | MySQL 8.0（独立实例，`utf8mb4_0900_ai_ci`） |
| 客户端 | Web: Dexie/IndexedDB；Android: expo-sqlite（同构表结构） |
| 真理来源 | 服务端 MySQL；客户端本地库是**读源**，不是真源 |

---

## 1. 设计总纲（六条不可动摇的规则）

1. **主键用 ULID（26 位字符串），不用自增。** 离线创建必须在无服务端参与时就能确定 id；自增必然导致"离线建的任务联网后换 id"，进而让所有引用失效。
2. **所有时间字段用 `DATETIME(3)`（毫秒）+ 独立 `tzid` 列。** 不存"看起来是本地时间"的字符串。
3. **所有删除都是软删（`deleted_at`）+ tombstone 保留 30 天。** 否则另一端会把"消失"误判为"本地新建"。
4. **变更水位用单表 `change_seq` 发号，绝不用自增主键。** 多表自增 id 交叉会让 `since=1234` 永久漏行。
5. **重复规则只在本地存 iCal 语义，Graph 侧是投影。** 不把微软的 `recurrence` 结构当模型。
6. **客户端永远不做"先删后建"来表达修改。** 那会产生幽灵和重复。

---

## 2. 通用字段约定（所有可同步表都带）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | `CHAR(26)` PK | ULID，客户端生成 |
| `user_id` | `CHAR(26)` | 单用户场景恒为同一值，保留以便扩展 |
| `rev` | `INT UNSIGNED` | 服务端维护的版本号，每次成功写入 +1 |
| `change_seq` | `BIGINT UNSIGNED` | 本次变更的水位号，`KEY idx_seq (change_seq)` |
| `updated_at` | `DATETIME(3)` | 服务端写入时间（不是客户端时间） |
| `deleted_at` | `DATETIME(3) NULL` | 软删标记 |
| `hlc_wall` | `BIGINT` | 客户端 HLC 墙钟毫秒 |
| `hlc_counter` | `INT UNSIGNED` | HLC 计数器 |
| `hlc_device` | `CHAR(26)` | 设备 id，用于同毫秒内定序 |

**HLC 定序规则**：比较 `(hlc_wall, hlc_counter, hlc_device)` 字典序，大者为"更晚"。
**时钟保护**：若 `hlc_wall` 与服务器时间偏差 > 5 分钟，服务端**改用服务器时间**覆盖（防止某台设备时钟错乱导致"永远赢"）。

### 2.1 水位发号

```sql
CREATE TABLE change_seq (
  id  TINYINT UNSIGNED NOT NULL PRIMARY KEY DEFAULT 1,
  seq BIGINT UNSIGNED NOT NULL DEFAULT 0
) ENGINE=InnoDB;
INSERT INTO change_seq (id, seq) VALUES (1, 0);

-- 每次写入，在同一事务内：
UPDATE change_seq SET seq = LAST_INSERT_ID(seq + 1) WHERE id = 1;
-- 然后在应用层取 LAST_INSERT_ID() 作为本行的 change_seq
```

**为什么必须同事务**：如果先提交数据行再取号，或先取号再提交，并发时会出现"序号大但数据还没提交"的空洞。客户端拉到空洞之上后，那条晚提交的行就再也拉不到了。`LAST_INSERT_ID(expr)` 的技巧让取号成为单语句原子操作，并与行写入共享事务边界。

### 2.2 Tombstone 保留与客户端重同步

- tombstone（`deleted_at IS NOT NULL` 的行）保留 **30 天**，由 `sync.cleanup_tombstones` 每日清理。
- 客户端 pull 时若 `cursor < min_available_seq`（即游标早于最早可用 tombstone），服务端返回：

```json
{ "resyncRequired": true, "reason": "cursor_too_old", "serverCursor": 84213 }
```

- 客户端收到后：清空本地业务表 → 全量拉取 → 重置 cursor。**UI 必须提示**「正在重建本地数据」，而不是静默卡住。

## 4. 表结构

### 4.1 `list`（清单）

```sql
CREATE TABLE list (
  id          CHAR(26)     NOT NULL PRIMARY KEY,
  user_id     CHAR(26)     NOT NULL,
  name        VARCHAR(64)  NOT NULL,
  kind        ENUM('inbox','normal','archive') NOT NULL DEFAULT 'normal',
  sort_order  INT          NOT NULL DEFAULT 0,
  rev         INT UNSIGNED NOT NULL DEFAULT 1,
  change_seq  BIGINT UNSIGNED NOT NULL,
  updated_at  DATETIME(3)  NOT NULL,
  deleted_at  DATETIME(3)  NULL,
  hlc_wall    BIGINT       NOT NULL,
  hlc_counter INT UNSIGNED NOT NULL DEFAULT 0,
  hlc_device  CHAR(26)     NOT NULL,
  KEY idx_seq (change_seq),
  UNIQUE KEY uk_inbox (user_id, kind, deleted_at)
) ENGINE=InnoDB;
```

`kind='inbox'` 为收集箱，每用户唯一（用 `uk_inbox` 唯一索引保证）。删除清单时任务 `list_id` 改指 inbox，**不级联删任务**。

### 4.2 `tag` / `task_tag`

```sql
CREATE TABLE tag (
  id CHAR(26) PRIMARY KEY, user_id CHAR(26) NOT NULL,
  name VARCHAR(32) NOT NULL, color_key TINYINT NOT NULL DEFAULT 0, -- 不存颜色值，只存设计 token 索引
  rev INT UNSIGNED NOT NULL DEFAULT 1, change_seq BIGINT UNSIGNED NOT NULL,
  updated_at DATETIME(3) NOT NULL, deleted_at DATETIME(3) NULL,
  hlc_wall BIGINT NOT NULL, hlc_counter INT UNSIGNED NOT NULL DEFAULT 0, hlc_device CHAR(26) NOT NULL,
  KEY idx_seq (change_seq),
  UNIQUE KEY uk_name (user_id, name, deleted_at)
) ENGINE=InnoDB;

CREATE TABLE task_tag (
  task_id CHAR(26) NOT NULL, tag_id CHAR(26) NOT NULL,
  change_seq BIGINT UNSIGNED NOT NULL, deleted_at DATETIME(3) NULL,
  hlc_wall BIGINT NOT NULL, hlc_counter INT UNSIGNED NOT NULL DEFAULT 0, hlc_device CHAR(26) NOT NULL,
  PRIMARY KEY (task_id, tag_id), KEY idx_seq (change_seq)
) ENGINE=InnoDB;
```

> `color_key` 是**设计 token 的索引**（0=灰, 1=蓝…），不是自由色值。瑞士风格不允许用户自选十六进制色，否则视觉体系立刻崩掉。

### 4.3 `task`（待办，核心表）

```sql
CREATE TABLE task (
  id            CHAR(26)     NOT NULL PRIMARY KEY,
  user_id       CHAR(26)     NOT NULL,
  list_id       CHAR(26)     NOT NULL,
  parent_id     CHAR(26)     NULL,          -- 子任务父级
  path          VARCHAR(96)  NOT NULL,      -- 物化路径 'rootid/parentid/'，避免递归 CTE（兼容 5.7 降级）
  depth         TINYINT      NOT NULL DEFAULT 0,

  title         VARCHAR(512) NOT NULL,
  note          TEXT         NULL,

  -- 时间
  due_date      DATE         NULL,          -- 仅日期（无时间的任务）
  start_at      DATETIME(3)  NULL,          -- 有时间的任务用这组
  end_at        DATETIME(3)  NULL,
  all_day       TINYINT(1)   NOT NULL DEFAULT 0,
  tzid          VARCHAR(64)  NOT NULL DEFAULT 'Asia/Shanghai',

  -- 分类与属性
  location      VARCHAR(256) NULL,
  priority      TINYINT      NOT NULL DEFAULT 0,   -- 0=无 1=低 2=中 3=高
  important     TINYINT(1)   NOT NULL DEFAULT 0,   -- 四象限纵轴
  urgent        TINYINT(1)   NOT NULL DEFAULT 0,   -- 四象限横轴
  quadrant      TINYINT      GENERATED ALWAYS AS (important * 2 + urgent) STORED,
  sort_order    INT          NOT NULL DEFAULT 0,   -- 手动排序

  -- 状态
  completed_at  DATETIME(3)  NULL,
  archived_at   DATETIME(3)  NULL,

  -- 重复（iCal 语义，仅系列母体有值）
  rrule         VARCHAR(512) NULL,          -- 'FREQ=WEEKLY;BYDAY=MO,WE,FR'
  rrule_until   DATETIME(3)  NULL,
  rrule_count   INT          NULL,
  series_id     CHAR(26)     NULL,          -- 例外实例指向母体

  -- 提醒
  remind_at     DATETIME(3)  NULL,
  remind_minutes INT         NULL,

  rev           INT UNSIGNED NOT NULL DEFAULT 1,
  change_seq    BIGINT UNSIGNED NOT NULL,
  updated_at    DATETIME(3)  NOT NULL,
  deleted_at    DATETIME(3)  NULL,
  hlc_wall      BIGINT NOT NULL, hlc_counter INT UNSIGNED NOT NULL DEFAULT 0, hlc_device CHAR(26) NOT NULL,

  KEY idx_seq (change_seq),
  KEY idx_list_due (user_id, list_id, completed_at, due_date),
  KEY idx_time (user_id, start_at),
  KEY idx_parent (parent_id),
  KEY idx_series (series_id),
  KEY idx_quadrant (user_id, quadrant, completed_at),
  FULLTEXT KEY ft_search (title, note) WITH PARSER ngram
) ENGINE=InnoDB;
```

> `quadrant` 用生成列而非应用层计算，让四象限查询（最高频查询）直接走索引。
> `FULLTEXT ... WITH PARSER ngram` 是中文搜索必需的；但**客户端搜索不走它**（本地库搜），它只服务于服务端兜底搜索与统计。
> `path` 物化路径让"某任务的全部子任务"变成 `WHERE path LIKE 'abc/%'`，一条索引查询搞定，不依赖递归 CTE（M0 若降级到 5.7 也无需改代码）。

### 4.4 `recur_exception`（重复的例外，最关键的一张辅助表）

```sql
CREATE TABLE recur_exception (
  id                CHAR(26)     NOT NULL PRIMARY KEY,
  user_id           CHAR(26)     NOT NULL,
  series_id         CHAR(26)     NOT NULL,     -- 母体 task.id 或 cal_event.id
  series_kind       ENUM('task','event') NOT NULL,
  original_start    DATETIME(3)  NOT NULL,     -- 该次在原系列中的原定开始（UTC 存，显示时转 tzid）
  override_start    DATETIME(3)  NULL,
  override_end      DATETIME(3)  NULL,
  override_title    VARCHAR(512) NULL,
  override_payload  JSON         NULL,         -- 其余被改字段的稀疏覆盖
  kind              ENUM('override','deleted') NOT NULL,
  rev               INT UNSIGNED NOT NULL DEFAULT 1,
  change_seq        BIGINT UNSIGNED NOT NULL,
  updated_at        DATETIME(3)  NOT NULL, deleted_at DATETIME(3) NULL,
  hlc_wall BIGINT NOT NULL, hlc_counter INT UNSIGNED NOT NULL DEFAULT 0, hlc_device CHAR(26) NOT NULL,
  UNIQUE KEY uk_series_start (series_id, original_start),
  KEY idx_seq (change_seq)
) ENGINE=InnoDB;
```

两组语义：
- `kind='override'` → 这次被改写（对应 iCal 的 RECURRENCE-ID + 属性覆盖）
- `kind='deleted'` → 这次被跳过（对应 iCal 的 EXDATE）

**为什么不用 `task.exdate` JSON 列**：例外需要参与增量同步（单独 `change_seq`）、需要单独记冲突、需要被单独软删。塞进 JSON 列后，任何一次例外修改都会让整个母体 `rev` 变化，导致大规模"假冲突"。

### 4.5 `habit` / `habit_log`

```sql
CREATE TABLE habit (
  id CHAR(26) PRIMARY KEY, user_id CHAR(26) NOT NULL,
  name VARCHAR(64) NOT NULL,
  type ENUM('boolean','count','duration') NOT NULL,   -- 习惯/计数/时长
  target_value INT NOT NULL DEFAULT 1,                -- 计数目标值 / 时长目标（分钟）
  unit VARCHAR(16) NULL,                              -- '页' '杯' '分钟'
  freq_kind ENUM('daily','weekly_n') NOT NULL DEFAULT 'daily',
  freq_per_week TINYINT NULL,                         -- freq_kind='weekly_n' 时有效
  remind_time TIME NULL,
  remind_enabled TINYINT(1) NOT NULL DEFAULT 1,
  start_date DATE NOT NULL,
  archived_at DATETIME(3) NULL,
  sort_order INT NOT NULL DEFAULT 0,
  rev INT UNSIGNED NOT NULL DEFAULT 1, change_seq BIGINT UNSIGNED NOT NULL,
  updated_at DATETIME(3) NOT NULL, deleted_at DATETIME(3) NULL,
  hlc_wall BIGINT NOT NULL, hlc_counter INT UNSIGNED NOT NULL DEFAULT 0, hlc_device CHAR(26) NOT NULL,
  KEY idx_seq (change_seq)
) ENGINE=InnoDB;

CREATE TABLE habit_log (
  habit_id CHAR(26) NOT NULL,
  log_date DATE NOT NULL,                  -- 打卡归属日（按用户时区）
  value    INT NOT NULL DEFAULT 1,         -- 计数累计 / 时长分钟
  done     TINYINT(1) NOT NULL DEFAULT 0,  -- 是否达标
  backfilled TINYINT(1) NOT NULL DEFAULT 0,
  note     VARCHAR(256) NULL,
  rev INT UNSIGNED NOT NULL DEFAULT 1, change_seq BIGINT UNSIGNED NOT NULL,
  updated_at DATETIME(3) NOT NULL, deleted_at DATETIME(3) NULL,
  hlc_wall BIGINT NOT NULL, hlc_counter INT UNSIGNED NOT NULL DEFAULT 0, hlc_device CHAR(26) NOT NULL,
  PRIMARY KEY (habit_id, log_date),
  KEY idx_seq (change_seq)
) ENGINE=InnoDB;
```

**`habit_log` 是 append-only 且幂等**：主键 `(habit_id, log_date)` 天然去重，两端同时打卡不会产生两条记录。计数型冲突按 `value = GREATEST(local, remote)` 合并（**不能相加**，否则同步一次数字翻倍——这是最容易踩的坑）。

> 连续天数、完成率、热力图全部在**应用层**用一次性查询最近 400 天的 log 计算（单人数据量 < 5000 行，内存里算 < 5ms）。不用窗口函数，因此不受 MySQL 5.7 降级影响。

## 5. 重复事件模型与 Graph 映射

### 5.1 本地模型（iCal 语义，唯一真源）

| iCal 概念 | 本项目落地 |
|---|---|
| DTSTART | `task.start_at` / `cal_event.start_at` + `tzid` |
| RRULE | `rrule` 列（字符串，如 `FREQ=WEEKLY;INTERVAL=1;BYDAY=MO,WE,FR`） |
| 结束条件 | `rrule_until`（UNTIL）或 `rrule_count`（COUNT），二者互斥，都为 NULL = 永不结束 |
| EXDATE | `recur_exception(kind='deleted')` |
| RECURRENCE-ID | `recur_exception(original_start)` |
| 例外覆盖 | `recur_exception(kind='override', override_*)` |

**支持的最小 RRULE 子集**（够用且能 1:1 映射 Graph）：

| 用户选择 | RRULE |
|---|---|
| 每天 | `FREQ=DAILY;INTERVAL=1` |
| 每 N 天 | `FREQ=DAILY;INTERVAL=N` |
| 每周（当前星期几） | `FREQ=WEEKLY;INTERVAL=1;BYDAY=<当日>` |
| 每周一三五 | `FREQ=WEEKLY;INTERVAL=1;BYDAY=MO,WE,FR` |
| 工作日 | `FREQ=WEEKLY;INTERVAL=1;BYDAY=MO,TU,WE,TH,FR` |
| 每月第 N 日 | `FREQ=MONTHLY;INTERVAL=1;BYMONTHDAY=N` |
| 每月最后一个周五 | `FREQ=MONTHLY;INTERVAL=1;BYDAY=FR;BYSETPOS=-1` |
| 每年 | `FREQ=YEARLY;INTERVAL=1` |

> **不支持**：`BYWEEKNO`、`BYYEARDAY`、多重 `BYSETPOS` 组合、`WKST` 非默认值。UI 上不暴露这些入口，从根上避免"能存不能同步"。

### 5.2 本地 → Graph 的映射表

| 本地操作 | Graph 请求 | 备注 |
|---|---|---|
| 创建系列 | `POST /me/events`，body 带 `recurrence: { pattern, range }` | range 见 5.3 |
| 改全部 | `PATCH /me/events/{seriesMasterId}` | 带 `If-Match` |
| 改单次 | ①`GET /me/events/{master}/instances?startDateTime=&endDateTime=` ②`PATCH /me/events/{occurrenceId}` | PATCH 后该实例 `type` 变 `exception`，`seriesMasterId` 指回母体 |
| 删单次 | 同上取 `occurrenceId` → `DELETE /me/events/{occurrenceId}` | **删后 Graph 不留痕**，本地必须自存 `kind='deleted'` 的例外 |
| 删全部 | `DELETE /me/events/{master}` | |
| 改本次及后续 | ①`PATCH master`，`recurrence.range.endDate = 目标日前一天` ②`POST` 一条新系列（`start` = 目标日，`recurrence` = 新规则） | **Graph 无原生 API，必须自己拆** |
| 删本次及后续 | 仅 ① 截断 master | 不新建 |

### 5.3 Graph 的两个硬边界（必须写进 UI 提示与日志）

1. **`range` 不支持"永不结束"**。Graph 只接受 `endDate` 或 `numberOfOccurrences`。本地"永不结束"的事件回写时，自动用 **`endDate = start + 10 年`**，并在本地标记 `rrule_until_is_proxy=1`；对账时容忍这 10 年边界，不报警。
2. **`pattern` 不完全等价**。`BYSETPOS=-1`（每月最后一个周五）要映射成 `relativeMonthly: { daysOfWeek:['friday'], index:'last' }`；`BYMONTHDAY=31` 映射成 `absoluteMonthly: { dayOfMonth:31 }`，微软侧遇到无 31 日的月份会跳过——与本地一致，可接受。

### 5.4 pattern 映射细则

```
本地 RRULE                          → Graph recurrence.pattern
FREQ=DAILY;INTERVAL=N               → { type:'daily', interval:N }
FREQ=WEEKLY;BYDAY=...;INTERVAL=N    → { type:'weekly', interval:N, daysOfWeek:['monday',...] }
FREQ=MONTHLY;BYMONTHDAY=N           → { type:'absoluteMonthly', interval:1, dayOfMonth:N }
FREQ=MONTHLY;BYDAY=XX;BYSETPOS=K    → { type:'relativeMonthly', interval:1, daysOfWeek:[...], index:'first'|'second'|'third'|'fourth'|'last' }
FREQ=YEARLY;BYMONTH=M;BYMONTHDAY=D  → { type:'absoluteYearly', interval:1, month:M, dayOfMonth:D }
```

反向（Graph → 本地）同理，遇到无法表达的 pattern 时：**落地为"非重复的独立事件集合"**（展开成 N 条），并标 `sync_state='readonly'`，避免每次同步都来回改写。

### 5.5 拆系列算法（"本次及后续"）

```ts
// 输入：seriesId, cutoffDate(用户选中的那一次的日期)
// 1) 校验 cutoff 是该系列的合法实例日
// 2) 计算原系列在 cutoff 之前的最后一次实例
// 3) PATCH master: recurrence.range.endDate = "cutoff 前一天"
// 4) 若原系列有 endDate/count，新系列继承剩余规则：
//    count' = count - 已过实例数（若原为 count 型）
// 5) POST 新系列：start = cutoff 当天同一时刻，rrule 用新规则
// 6) 把 cutoff 之后所有 recur_exception 的 series_id 重映射到新系列 id
// 7) 若任一步失败：回滚前先尝试恢复 master 的 endDate（补偿事务）
```

**第 6 步是最容易漏的**：如果不重映射例外，那些"仅在本次改过时间"的实例会变成孤儿，对账时被判为"未知事件"而重复创建。

## 6. 同步协议

### 6.1 拉取（pull）

```
POST /api/sync/pull
{ "cursor": 84100, "limit": 500 }

200 {
  "changes": [
    { "table":"task", "id":"01J...", "rev":7, "seq":84113, "payload":{...} },
    { "table":"task", "id":"01J...", "rev":8, "seq":84114, "deletedAt":"2026-11-23T01:02:03.123Z" }
  ],
  "nextCursor": 84114,
  "hasMore": false,
  "resyncRequired": false
}
```

服务端实现（单次查询，`UNION ALL` 各表后按 seq 排序）：

```sql
SELECT 'task' AS t, id, rev, change_seq, NULL AS deleted_at FROM task      WHERE user_id=? AND change_seq > ? 
UNION ALL
SELECT 'list', id, rev, change_seq, deleted_at FROM list                   WHERE user_id=? AND change_seq > ?
UNION ALL
SELECT 'tag',  id, rev, change_seq, deleted_at FROM tag                    WHERE user_id=? AND change_seq > ?
UNION ALL
SELECT 'habit',id, rev, change_seq, deleted_at FROM habit                  WHERE user_id=? AND change_seq > ?
UNION ALL
SELECT 'cal_event', id, rev, change_seq, deleted_at FROM cal_event          WHERE user_id=? AND change_seq > ?
UNION ALL
SELECT 'recur_exception', id, rev, change_seq, deleted_at FROM recur_exception WHERE user_id=? AND change_seq > ?
ORDER BY change_seq ASC
LIMIT 501;   -- 多取 1 条判断 hasMore
```

命中行后按 `(table,id)` 二次取完整 payload（批量 `IN`，按表分组，最多 6 条查询）。

**约束**：单次响应 ≤ **500 行 / 1MB**；客户端必须循环拉到 `hasMore=false` 才算同步完成，中途失败保留上次成功游标（不推进）。

### 6.2 推送（push）

```
POST /api/sync/push
{ "deviceId":"01J...", "ops":[
  { "opId":"01J...", "table":"task", "action":"update", "id":"01J...",
    "baseRev":6, "fields":{ "title":"新标题", "due_date":"2026-11-24" },
    "hlc":{ "wall": 1795000000123, "counter":0, "device":"01J..." } }
]}

200 { "results":[
  { "opId":"...", "status":"applied",  "rev":7, "seq":84120 },
  { "opId":"...", "status":"conflict", "rev":7, "conflicts":[{"field":"due_date","local":"2026-11-24","remote":"2026-11-25"}], "serverPayload":{...} },
  { "opId":"...", "status":"duplicate" },
  { "opId":"...", "status":"rejected", "reason":"not_found" }
], "serverCursor": 84120 }
```

状态语义：

| status | 客户端处理 |
|---|---|
| `applied` | 更新本地 `rev`，从队列移除 |
| `conflict` | 非冲突字段已合并，冲突字段**保留本地值 + 记入冲突待决**，不自动丢弃 |
| `duplicate` | 视为 `applied`（幂等重放），从队列移除 |
| `rejected` | 从队列移除并记录（不无限重试），UI 标注该条"未能保存" |

**顺序要求**：`push → pull → 应用 → 若 hasMore 继续 pull`。先 push 是为了让本地意图优先落库，避免"拉到的远端旧值覆盖本地新值"。

### 6.3 服务端处理单个 op 的事务边界

```sql
START TRANSACTION;
  -- 1) 幂等检查
  SELECT ... FROM op_applied WHERE op_id = ? FOR UPDATE;   -- 命中则直接返回 duplicate
  -- 2) 取号
  UPDATE change_seq SET seq = LAST_INSERT_ID(seq + 1) WHERE id = 1;
  -- 3) 读取当前行（带 FOR UPDATE）
  SELECT rev, hlc_wall, hlc_counter, hlc_device FROM task WHERE id = ? FOR UPDATE;
  -- 4) baseRev 校验 + 字段级合并（在应用层算）
  -- 5) 写行（rev+1, change_seq=新号, hlc=客户端值或服务器值）
  UPDATE task SET ..., rev = rev + 1, change_seq = ?, updated_at = NOW(3) WHERE id = ?;
  -- 6) 记 op_applied 与 conflict_log
COMMIT;
```

**一个 op 一个事务**，不做批量事务（避免一个坏 op 回滚整批）。批量 op 的响应里逐条给结果。

### 6.4 客户端应用远端变更（防闪烁）

- 客户端记录 `lastPushSeq`（自己最后一批 push 得到的 `serverCursor`）。
- pull 到的行若 `seq <= lastPushSeq` 且 `rev` 与本地相同 → 视为自回声，跳过（不触发动画、不改选中态）。
- 若 `seq > lastPushSeq` 但同 `rev` → 可能是自己的 push 被其他设备看到，正常应用但**不弹提示**。
- 应用时若该行正被用户编辑（抽屉打开且有未保存修改），**进 shadow 区**，等抽屉关闭再合并——避免用户正在打字时输入框被远端值覆盖。

## 7. 冲突解决规则

### 7.1 三层机制

1. **字段掩码**：客户端 push 时只带真正改动的字段（`fields`），服务端只对这些字段做裁决，其余字段不动。
2. **`baseRev` 校验**：`baseRev == 当前 rev` → 无并发，直接应用；不等 → 进入字段级比对。
3. **HLC 定序**：仅当**同一字段被双方都改**时，用 HLC 比较定胜负。

### 7.2 判定矩阵（开发时逐行实现）

| 场景 | 规则 | 结果 |
|---|---|---|
| 本地改 A 字段，远端改 B 字段 | 都保留 | 自动合并，无提示 |
| 双方改同一字段 | HLC 大者胜，败者值写入 `conflict_log` | 胜者生效，UI 在详情页显示「有另一版本」可一键切回 |
| 「完成」状态冲突（一方勾掉，一方取消勾） | **完成优先**（`completed_at` 非 NULL 胜） | 不会被远端"复活"，防误触 |
| 本地删除，远端修改 | **删除优先** | 远端修改丢弃，记 conflict_log（可恢复） |
| 本地修改，远端删除 | **删除优先** | 同上 |
| 移动清单（list_id 冲突） | HLC 定序 | 整字段二选一 |
| 优先级 / 象限（important, urgent） | 视作**一个四象限字段**整体定序 | 不拆成两个布尔分别裁决（否则会出现不可能的组合） |
| 标签集合 | **取并集**，删除需显式 `remove_tag` op | 集合类数据用并集比用 LWW 更符合直觉 |
| 子任务 parent_id 冲突 | 若造成环或超 3 层 → 拒绝，落回原父级 + 记 conflict_log | 防止树结构损坏 |
| `rrule` / 重复规则 | **原子块**，整块二选一，不拆字段 | 拆字段会产生无人能解析的规则 |
| `habit_log` 同 `(habit_id, date)` | 幂等 upsert；计数型 `value = GREATEST(a,b)` | **绝不相加**（会翻倍） |
| `recur_exception` 同 `(series_id, original_start)` | 唯一键冲突 → 后到者按 HLC 覆盖，`kind` 以 `deleted` 优先 | 删过的不会被"复活" |
| `delete` 与 `override` 同时到 | `deleted` 胜 | |
| 时钟偏差 > 5 分钟 | 服务端用服务器时间覆盖 HLC | 防单台设备时钟错乱永久获胜 |

### 7.3 为什么不用 CRDT

单用户双设备，真实并发概率极低（一年可能几十次）。CRDT 的代价是：tombstone 无法安全 GC、存储与索引膨胀、调试成本极高。更关键的是——**最难的那一段（Outlook）不是 CRDT 系统**，无论如何都要在边界退化成 LWW。收益不匹配成本。因此选择"字段级 LWW + 硬语义规则"，并接受"极少数重叠修改需要用户裁决一次"。

## 8. 客户端离线队列

### 8.1 队列结构（本地库）

```ts
type LocalOp = {
  opId: string;          // ULID，幂等键
  table: TableName;
  action: 'create' | 'update' | 'delete';
  id: string;
  baseRev: number;       // create 时为 0
  fields?: Record<string, unknown>;
  hlc: { wall: number; counter: number; device: string };
  createdAt: number;     // 本地时间，仅用于排序与 UI 展示
  attempts: number;
  lastError?: string;
};
```

### 8.2 合并（coalescing）规则

同一 `(table, id)` 的多个 update 在 flush 前合并：

- `create` + 多个 `update` → 合并成一个 `create`（带最终字段集）；`baseRev = 0`。
- `update` + `update` → 合并 `fields`（后者覆盖同名字段）。
- `update` + `delete` → 只保留 `delete`（若原记录从未上传，直接本地物理删除，不发任何 op）。
- `create` + `delete`（同一记录从未成功上传）→ 队列里两条都删掉，本地物理删除。

**队列上限**：2000 条。超过时拒绝新操作并提示「请先联网同步」——比静默丢数据好。

### 8.3 flush 策略

| 触发 | 行为 |
|---|---|
| 操作后 2s（防抖） | 若在线，发起 flush |
| 网络恢复（`online` 事件） | 立即 flush |
| 前台聚焦 | 立即 flush + pull |
| 定时（每 60s，仅在线的前台页面） | flush + pull |
| 连续失败 | 指数退避 2s→4s→8s→16s→32s，封顶 60s；连续 8 次失败则停自动重试，转手动 |

### 8.4 Web 多标签页互斥

```ts
// 每轮同步取一次锁，不常驻（后台标签页会被冻结，常驻锁会变僵尸）
const lock = await navigator.locks.request('grid-sync', { ifAvailable: true }, async (l) => {
  if (!l) return false;          // 别的标签页正在同步，本轮跳过
  await doFlush();
  await doPull();
  return true;
});
```

- `BroadcastChannel('grid-db')` 只做一件事：通知其他标签页「数据变了，重读 IDB」。**不承担互斥**（无原子性、消息可能丢）。
- 兜底：`op_id` 的唯一索引让重复 push 无害。**最终一致靠服务端约束，不靠浏览器端完美互斥。**
- 老浏览器无 Web Locks → 退化为 `localStorage` 租约（写时间戳 + 8 秒心跳），冲突概率上升但仍有 op_id 兜底。

## 9. Outlook 三方合并

### 9.1 三方

| 名称 | 来源 | 存储 |
|---|---|---|
| base | 上次同步成功时的字段快照 | `cal_event.synced_snapshot` |
| local | 用户当前在 GRID 里的改动 | `cal_event` 当前值 + `sync_state='local_dirty'` |
| remote | Graph 返回的事件 | delta / GET 结果 |

### 9.2 合并算法

```
for each field in (subject, start, end, location, body, isAllDay, reminders, rrule):
  if local == base and remote != base        → 取 remote
  else if local != base and remote == base   → 取 local，标 pending_push
  else if local != base and remote != base:
      if local != remote:
          if 本地有显式编辑标记(dirty_fields 含该字段) → 取 local，记 conflict_log
          else                                        → 取 remote
```

原则：**用户的显式编辑优先于微软侧的被动变化**（例如 Outlook 客户端把会议挪了 15 分钟，但用户在 GRID 里主动改了标题——标题取本地，时间取远端，双双成功）。

### 9.3 写回与失败处理

| 环节 | 做法 |
|---|---|
| 携带 | `PATCH` 带 `If-Match: <ms_etag>` |
| 412 Precondition Failed | 远端已变 → 重新 `GET` → 重跑三方合并 → 重试（最多 3 次） |
| 成功 | 立刻写回新 `etag`、`synced_snapshot`、`sync_state='synced'`，`op_applied` 记指纹 |
| self-echo | delta 回来的 `etag` 等于刚写入值 → 跳过 UI 更新 |
| 429 | 读 `Retry-After`，`next_run_at += Retry-After + jitter` |
| 4xx（非 429/412） | 永久失败 → `status='dead'` + `sync_state='failed'` + UI 提示「该事件未能同步到 Outlook」 |
| 5xx | 退避重试（1s→2s→4s→8s→16s，5 次后入死信） |
| 熔断 | 同一 `entity_id` 连续 3 次失败 → 该实体暂停回写 30 分钟 |

**防死循环三件套**：`op_id` 唯一键、`op_applied` 指纹、`etag` 自回声判定。缺任何一个都会出现"改一次推十次"。

### 9.4 单次删除的落地（P1）

```
1. 本地写 recur_exception(kind='deleted', original_start=X)
2. 查 cal_event 里该系列的 series_master_id
3. GET /me/events/{master}/instances?startDateTime=X-1d&endDateTime=X+1d
4. 在结果中按 start 匹配 X（容忍 ±1 分钟）
5. DELETE /me/events/{occurrenceId}
6. 若第 4 步匹配不到（已被别人删了）→ 视为成功
```

**Graph 删掉这一天后不会留下任何记录**，因此第 1 步的本地 `deleted` 例外是唯一凭证。夜间对账时若发现该次"在 Graph 里消失了"，正确的判断是"确实删了"，而不是"要重新创建"。

### 9.5 夜间对账（P1）

每日 04:00 执行：

```
1. 拉取窗口内全部事件（calendarView，非 delta）
2. 对每个本地系列：用 RRULE 展开成预期实例集
3. 比对：Graph 有 / 本地预期有
   - Graph 有、本地无预期且不是例外 → 幽灵：告警 + 本地补建（标 orphan）
   - 本地预期有、Graph 无 → 丢失：告警 + 重建
   - 例外集合与 Graph 不符 → 修正 recur_exception
4. 结果写 health_log 并在 UI 的「同步诊断」页展示最近一次对账摘要
```

对账**不自动修复重复系列结构冲突**（怕越修越乱），只告警 + 提供"一键重建该系列"的手动入口。

| 项 | 措施 |
|---|---|
| 令牌存储 | AES-256-GCM，一记录一 nonce，AAD 绑定 `account_id`；密钥走 systemd `EnvironmentFile`，**不入库、不进 git** |

## 11. 迁移与版本演进

- Drizzle migrations 按序号提交（`0001_init.sql`…），**只增不改**。
- 客户端本地库有独立版本号（Dexie `version(n)` / expo-sqlite `PRAGMA user_version`），升级时执行本地迁移脚本，失败则清库重拉（数据在服务端，可接受）。
- 协议版本：`/api/sync/pull` 与 `push` 接受 `X-Client-Version` 头，服务端对过旧客户端返回 `426 Upgrade Required`，前端拦截并提示刷新。
- **不兼容变更的判定标准**：任何让"旧客户端读到新字段后行为错误"的改动，都必须先升协议版本号，再让服务端同时支持两个版本至少 30 天。

## 12. 本文件里最容易在实现阶段翻车的五个点

1. **`change_seq` 不在事务内取号** → 客户端永久漏行，且症状偶发、事后才发现。
2. **`habit_log` 计数型冲突相加** → 同步一次数值翻倍。
3. **"本次及后续"拆系列后不重映射 `recur_exception.series_id`** → 例外变孤儿，夜间对账批量误报。
4. **把 `nextLink` 当 `deltaLink` 存** → 分页未走完就重置，中间事件永久丢失。
5. **pull 应用时覆盖正在编辑的输入框** → 用户打字被吞，且极难复现（只在双端同时操作时出现）。
