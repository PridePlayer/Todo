### 1.1 为什么是单进程（而不是 API + worker 双进程）

标准做法是拆两个进程，理由是"同步任务可能拖垮接口"。但在 2C2G 且已有其他服务的机器上，多一个 Node 运行时就是多 60~90MB 常驻。因此本项目改为**同一进程内用并发与超时约束替代进程隔离**：

- 对外 API 与 Graph 同步任务共用事件循环（都是 I/O 密集，不阻塞）；
- Graph 调用并发上限 **2**，单次请求超时 **15s**，单任务总超时 **60s**；
- 调度器每 30 秒 tick 一次，单 tick 最多领取 **3** 个任务；
- 代码层面把同步内核写成独立模块，**预留 `WORKER_MODE=1` 启动参数**，当实测内存/延迟不可接受时，可零改动拆成第二个 systemd 服务。

这是有意识的取舍：用"可能偶尔慢 1~2 秒"换"少 90MB 常驻"。若后续升配到 4G，直接开 `WORKER_MODE=1` 即可。

## 2. 技术选型定稿

| 层 | 选型 | 版本约束 | 理由 | 备选与放弃原因 |
|---|---|---|---|---|
| Web 框架 | React + Vite | React 19 / Vite 7 | 桌面级键盘与密集视图控制力最强 | Next.js：本项目不需要 SSR/SEO，多一层运行时吃内存 |
| 路由 | TanStack Router | v1 | 类型安全路由 + 视图状态可放 URL | React Router：类型支持弱 |
| 服务端状态 | TanStack Query | v5 | 与本地库分层（本地库是源，Query 只管请求生命周期） | SWR：功能更薄 |
| 样式 | CSS Modules + 设计 token（CSS 变量） | — | 瑞士风格靠精确网格，不需要原子类堆叠 | Tailwind：网格间距易失控；Styling 语义弱 |
| 拖拽 | `@dnd-kit/core` | v6 | 唯一提供完整键盘无障碍的拖拽库 | react-beautiful-dnd：已停维护且无键盘替代 |
| 日期 | `date-fns` + `date-fns-tz` | v4 | 树摇友好、无 moment 包袱 | Day.js：时区插件行为不够显式 |
| 重复规则 | `rrule`（本地展开）+ 自研 Graph 映射 | — | RRULE 展开是成熟算法，不重写 | 自研 RRULE：不值得 |
| 本地库（Web） | Dexie（IndexedDB 封装） | v4 | 事务、索引、迁移齐全 | 裸 IndexedDB：样板代码过多；SQLite-WASM：包体 +3MB |
| 本地库（Android） | `expo-sqlite` | SDK 58 | 官方维护；**SDK 58 已移除 libSQL**，不做远程直连 | WatermelonDB：与 Expo 新架构适配滞后 |
| Android 外壳 | Expo SDK 58（RN 0.88，New Architecture 强制） | — | 本地通知 + SQLite 齐全；`prebuild + gradlew` 可完全离线构建 | 纯 RN CLI：自己维护原生工程；Flutter：Web 端弱 |
| 共享层 | `packages/core`（TS，zod 单一事实源） | — | 双端同一套模型/同步引擎/校验，杜绝双端语义漂移 | 各端各写：必然漂移 |
| 后端 | Fastify | v5 | 低内存、schema 校验原生、插件体系够用 | Express：性能与校验弱；Nest：2C2G 上太重 |
| ORM | Drizzle ORM | latest | 类型安全、迁移可读、SQL 可控（避免方言坑） | Prisma：引擎常驻内存 +150MB，2C2G 不可接受 |
| 数据库 | MySQL 8.0 独立实例 | 8.0.x | 用户现有栈、宝塔可管；5.7 不动 | 8.4 LTS 更好但宝塔多版本工具只到 8.0（见 §3） |
| 调度 | `job` 表 + node-cron + `FOR UPDATE SKIP LOCKED` | — | 省一个 Redis 进程（约 60~100MB） | BullMQ：必须 Redis；node-cron 纯内存：重启丢任务 |
| 日志 | pino + pino-roll | — | 结构化、低开销 | winston：更重 |
| 进程守护 | systemd | — | 宝塔的 PM2 会多一层；systemd 可精确限内存 | PM2：cluster 模式在单用户场景只增内存 |
| 令牌加密 | Node `crypto` AES-256-GCM | — | 无外部依赖 | KMS：自托管无此条件 |

## 3. 数据库：MySQL 8.0 独立实例

### 3.1 为什么是独立实例而不是升级现有 5.7

| 方案 | 内存 | 风险 | 结论 |
|---|---|---|---|
| 升级现有 5.7 → 8.0 | 省一份实例内存 | 停机 + 认证插件 `caching_sha2_password` + `ONLY_FULL_GROUP_BY` 严格化，**可能拖死服务器上其他站点** | 否决 |
| 复用 5.7 建单库 | 最省 | 5.7 已 EOL 且无窗口函数/CTE | 作为 M0 闸门的降级方案 |
| **多版本工具起 8.0 独立实例（端口 3307）** | +约 350MB | 隔离干净，其他站点零影响 | **采用** |

**已知缺陷**：MySQL 8.0 已于 2026-04-21 EOL，不再有安全补丁。缓解措施：
1. 实例只绑 `127.0.0.1`，`bind-address = 127.0.0.1`，绝不开放 3306/3307 到公网（宝塔安全组同步检查）；
2. 专用账号 `grid_rw` 只授权 `grid` 单库，禁用 `GRANT`/`FILE` 权限；
3. 文档留出迁移路径：宝塔后续支持 8.4 时，按 `mysqldump → 8.4 实例 → 校验 → 切端口` 三步走，应用层无需改动（Drizzle 方言一致）。

### 3.2 `/etc/mysql-8.0/my.cnf` 关键参数（2C2G 专用）

```ini
[mysqld]
bind-address            = 127.0.0.1
port                    = 3307
datadir                 = /www/server/data-8.0
socket                  = /tmp/mysql-8.0.sock
character-set-server    = utf8mb4
collation-server        = utf8mb4_0900_ai_ci
default-time-zone       = '+08:00'

# —— 内存（这是全文最关键的四行）——
innodb_buffer_pool_size = 128M
performance_schema      = OFF
max_connections         = 20
table_open_cache        = 400
thread_cache_size       = 8
innodb_log_buffer_size  = 8M

# —— 单用户场景，写入极少 ——
innodb_flush_log_at_trx_commit = 1
innodb_io_capacity             = 200
sync_binlog                    = 1
binlog_expire_logs_seconds     = 604800   # 7 天，从 30 天默认降下来省磁盘

# —— 严格模式（8.0 默认已开，显式声明）——
sql_mode = ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
```

> `performance_schema = OFF` 单独能省 100~200MB，代价是没有细粒度性能视图——单用户场景用慢查询日志代替即可（`slow_query_log = ON`, `long_query_time = 0.3`）。

### 3.3 建库与账号

```sql
CREATE DATABASE grid CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'grid_rw'@'127.0.0.1' IDENTIFIED BY '<强密码>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES ON grid.* TO 'grid_rw'@'127.0.0.1';
FLUSH PRIVILEGES;
```

应用连接池：`connectionLimit: 8`，`idleTimeout: 30000`，`enableKeepAlive: true`。**不设 `multipleStatements`**。

## 5. 认证与会话

### 5.1 单用户模型

- 用户表只有一条记录（首次部署时用 CLI 创建：`pnpm --filter server seed:user --email x --password y`）。
- 密码哈希 **argon2id**（`memoryCost: 19456, timeCost: 2, parallelism: 1`，约 19MB 峰值、50ms 耗时）。
- 密码最少 12 位；连续 5 次失败锁定 10 分钟（内存 Map + DB 双重记录，重启不丢）。

### 5.2 Web：Cookie 会话

| 项 | 值 |
|---|---|
| Cookie 名 | `__Host-grid_s` |
| 属性 | `HttpOnly; Secure; SameSite=Lax; Path=/` |
| 内容 | 256-bit 随机 session id（不塞 JWT，便于服务端即时吊销） |
| 服务端存储 | `session` 表：`id_hash`（SHA-256）、`created_at`、`last_seen_at`、`user_agent`、`ip_hash` |
| 有效期 | 30 天滑动续期；绝对上限 90 天 |
| CSRF | 双提交：`X-CSRF-Token` 头 + `csrf` 非 HttpOnly Cookie；所有 `POST/PATCH/DELETE` 校验 |

### 5.3 Android：设备令牌

| 项 | 值 |
|---|---|
| 令牌 | 32 字节随机，Base64URL 编码，前缀 `grd_` |
| 存储 | 服务端只存 `SHA-256(token)`；客户端存 `expo-secure-store`（Android Keystore 支持） |
| 有效期 | 180 天，过期前 7 天自动静默轮换（旧令牌保留 24 小时宽限） |
| 吊销 | 设置页「注销此设备」→ 删除该行；下次请求 401 |
| 传输 | `Authorization: Bearer grd_xxx` |

### 5.4 登出清理清单（必须逐项执行，否则是安全事故）

Web：清 Dexie 全库 → 清 `localStorage`（偏好/游标）→ 清内存 store → 服务端删 session → 跳登录。
Android：`SQLiteDatabase.deleteDatabase()` → `SecureStore.deleteItemAsync` → 取消所有已排程的本地通知 → 清 AsyncStorage → 服务端吊销设备令牌。

## 6. Outlook / Microsoft Graph 集成

### 6.1 前置条件（用户需在 Azure 门户完成）

| 步骤 | 配置值 |
|---|---|
| 注册应用 | Azure 门户 → Entra ID → 应用注册 → 新注册 |
| 支持的账户类型 | **`AzureADandPersonalMicrosoftAccount`**（同时支持个人 MSA 与工作账号） |
| 重定向 URI | 平台选 **Web**，URI = `https://todo.<你的域名>/api/oauth/microsoft/callback` |
| 客户端密码 | 新建 secret，24 个月有效期，**到期前 30 天必须更换**（写进日历提醒） |
| API 权限（委托） | `offline_access`、`User.Read`、`Calendars.ReadWrite` |
| 是否需要管理员同意 | 个人账号：不需要；公司租户：可能需管理员批准（文档给审批话术模板） |
| 已知约束 | 该 audience 最多 30 个权限、最多 2 个 client secret |

> **最重要的隐藏约束**：个人 Microsoft 账号**不支持 client credentials（app-only）流**。这意味着服务端无法"自己"同步，必须依赖 delegated refresh token。refresh token 一旦失效（改密码、撤销授权、90 天不用），只能重新走一次交互登录。**这是整套方案最脆弱的一环，必须在 UI 上显式暴露**（见 §6.6）。

### 6.2 授权流程（Authorization Code + PKCE）

```
1. 用户点「连接 Outlook」
2. 服务端生成 state（32B 随机）+ code_verifier，把 {state → code_verifier, expires_at} 写入 oauth_state 表
3. 302 到 https://login.microsoftonline.com/common/oauth2/v2.0/authorize
   ?client_id=...&response_type=code&redirect_uri=...&response_mode=query
   &scope=offline_access%20User.Read%20Calendars.ReadWrite
   &state=...&code_challenge=...&code_challenge_method=S256
4. 用户登录并同意 → 回跳 /api/oauth/microsoft/callback?code=...&state=...
5. 服务端校验 state（一次性消费，5 分钟过期，失败即拒）
6. POST /token 用 code + code_verifier 换 {access_token, refresh_token, expires_in, scope}
7. 令牌加密入库 calendar_account；立刻执行一次全量同步（job: calendar.full_sync）
8. 重定向到 /settings/calendar?connected=1
```

**安全要点**：`state` 必须服务端存储并在回调时删除（防重放）；`code_verifier` 不落日志；回调路由限流 10 次/分钟；回调错误不把 `error_description` 原样回显（防注入）。

### 6.3 令牌存储与刷新

```ts
// 加密：AES-256-GCM，一记录一 nonce，AAD 绑定账号 id
key        = Buffer.from(process.env.TOKEN_ENC_KEY, 'base64')  // 32 字节，不入库
cipher     = createCipheriv('aes-256-gcm', key, nonce /*12B*/)
cipher.setAAD(Buffer.from(accountId))
ciphertext = cipher.update(plaintext, 'utf8') + cipher.final()
tag        = cipher.getAuthTag()                                // 16B，单独存列
// 存储：access_token_enc, access_token_iv, access_token_tag, 同构三列存 refresh_token
```

| 策略 | 做法 |
|---|---|
| 刷新时机 | access_token 剩余有效期 < 5 分钟时刷新 |
| 并发控制 | `calendar_account.refreshing_at` 加行锁；10 秒内重复请求直接复用结果（防抖） |
| 失效率处理 | 返回 `invalid_grant` → 置 `status='revoked'` → 前端红色通栏「Outlook 授权已失效，请重新连接」 |
| 密钥轮换 | `TOKEN_ENC_KEY_V2` 存在时，启动后后台逐条重加密并标记 `token_version` |
| 日志 | 任何令牌内容绝不进日志；pino redact 配置 `['req.headers.authorization', '*.access_token', '*.refresh_token']` |

### 6.4 增量同步设计

两条通道，职责不同：

| 通道 | 端点 | 用途 | 频率 |
|---|---|---|---|
| **主通道（窗口）** | `/me/calendarView/delta?startDateTime=&endDateTime=` | 用户可见范围（今天 ±60 天）的变更，直接驱动界面 | 前端在线时 60s 一次；收到 304/空则跳过 |
| **辅通道（全天候）** | `/me/events/delta` | 发现窗口外的新增与删除（`@removed`），只写库不触发 UI | 每日 03:00 一次 |
| 兜底对账 | `calendarView` 全窗口拉取 + 本地比对 | 修复幽灵/丢失（P1 阶段与重复事件一起上） | 每日 04:00 |

**关键实现细节**：

1. `deltaLink` 原样存字符串，**绝不能把 `nextLink` 当 `deltaLink` 存**（分页还没走完）。
2. 收到 `410 Gone` 或 body 含 `resyncRequired` → 清空该通道游标，做一次窗口全量重建。
3. `events/delta` 返回的条目字段极少（`id/type/start/end`），需要 `POST /$batch` 批量补详情（每批 ≤ 20 个）。
4. 事件 id 与 `iCalUId` 都要存：`id` 会因移动日历而变，`iCalUId` 稳定，用它做跨端身份。
5. 取消的事件以 `@removed` 出现在 delta 结果里，必须走软删而不是忽略。

### 6.5 回写与限流

| 项 | 策略 |
|---|---|
| 写回时机 | 客户端编辑后 3 秒防抖（拖拽改期场景）→ 服务端入 `outbox` 队列 → 调度器 30s tick 处理 |
| 幂等 | 每条 outbox 带 `op_id` + `local_rev`；已成功的 op 在 `op_applied` 表留指纹，重放直接跳过 |
| 乐观并发 | PATCH 必带 `If-Match: <etag>`；412 表示远端已变 → 重新 GET → 三方合并 → 重试（最多 3 次） |
| 自回声 | delta 回来的 `@odata.etag` 等于本地刚写入的 etag → 判为自回声，跳过 UI 更新只更新本地快照 |
| 限流 | Graph 约 10,000 请求/10 分钟/应用/邮箱。实现统一 `graphFetch` 包装：429 读 `Retry-After` 退避 + 抖动；并发 ≤ 2 |
| 失败分级 | 4xx（除 429）= 永久失败 → `dead_letter` 状态 + UI 提示；429/5xx = 可重试，指数退避 1s→2s→4s→8s→16s，超 5 次进死信 |
| 熔断 | 同一 `(resource_id, 字段集)` 连续失败 3 次 → 熔断 30 分钟，UI 显示「同步受阻」 |

### 6.6 服务器承担的同步职责（明确边界）

| 职责 | 是否承担 | 说明 |
|---|---|---|
| 增量拉取 | ✅ | 窗口 delta 按需 + 全天候 delta 夜跑 |
| 变更推送（Graph webhook） | ❌ | **不做**。个人账号的 subscription 最长约 3 天必须续订、需公网回调、增加攻击面；单用户场景轮询足够。P2 若需要再加 |
| 向客户端推送 | ❌ | 客户端主动轮询（在线 60s）；Android 前台时同步，后台靠本地闹钟 + 打开时补齐 |
| 冲突检测 | ✅ | 字段级比对 + 硬语义规则（详见 03） |
| 重试队列 | ✅ | `outbox` + `dead_letter` |
| 限流处理 | ✅ | 全局令牌桶 + `Retry-After` 遵从 |
| 离线操作合并 | ✅ | 服务端收到 push 时按字段合并，冲突字段留双方值 |
| 重复事件投影 | ✅（P1） | 截断系列 / 删除单次 / 夜间对账 |

## 7. 客户端同步机制（架构层）

完整协议见 `03-数据模型与同步策略.md`，此处只列架构决策：

| 决策 | 选择 | 理由 |
|---|---|---|
| 读源 | 本地库 | 毫秒级响应，离线可用 |
| 写路径 | 本地事务 + 队列 | 保证"操作立即生效"，UI 不做乐观回滚闪烁 |
| 水位 | 服务端 `change_seq` 单表发号 | 自增主键会因多表交叉乱序导致客户端永久漏行 |
| 推送时机 | 在线 60s 轮询 + 操作后 2s 触发 + 前台聚焦时立即 | 无长连接（2C2G 上 SSE/WebSocket 连接数虽少但省掉一层复杂度） |
| Web 多标签页 | Web Locks（每轮取锁，不常驻）+ BroadcastChannel 通知 | 后台标签页会被冻结，常驻锁会变僵尸 leader |
| 幂等 | 服务端 `op_id` 唯一索引 | 不依赖浏览器端完美互斥 |

> 说明：不做 WebSocket/SSE 是有意识的减配。单用户、变更频率低（每天几十次），60 秒轮询的体验损失远小于维持一条长连接的运维与内存成本。若后续要"另一台设备改动 2 秒内可见"，再加 SSE 即可（架构上已在 API 层预留 `/api/events/stream` 路由位）。

## 8. 定时任务与队列

### 8.1 表驱动队列（替代 Redis + BullMQ）

```sql
CREATE TABLE job (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  type          VARCHAR(48)  NOT NULL,
  payload       JSON         NOT NULL,
  run_at        DATETIME(3)  NOT NULL,
  status        ENUM('pending','running','done','dead') NOT NULL DEFAULT 'pending',
  attempts      TINYINT UNSIGNED NOT NULL DEFAULT 0,
  max_attempts  TINYINT UNSIGNED NOT NULL DEFAULT 5,
  last_error    TEXT NULL,
  locked_at     DATETIME(3) NULL,
  created_at    DATETIME(3)  NOT NULL,
  KEY idx_claim (status, run_at),
  KEY idx_type  (type, status)
) ENGINE=InnoDB;
```

领取任务用 MySQL 8 的 `SKIP LOCKED`（**5.7 不支持，这也是必须 8.0 的实际理由之一**）：

```sql
START TRANSACTION;
SELECT id FROM job
 WHERE status = 'pending' AND run_at <= NOW(3)
 ORDER BY run_at LIMIT 3
 FOR UPDATE SKIP LOCKED;
UPDATE job SET status='running', locked_at=NOW(3), attempts=attempts+1 WHERE id IN (...);
COMMIT;
```

### 8.2 任务清单

| 任务 | 触发 | 说明 |
|---|---|---|
| `graph.refresh_token` | access_token 剩余 < 5min，被调用前触发 | 单飞锁 |
| `graph.pull_window` | 客户端在线时每 60s；每日 03:00 | 窗口 delta |
| `graph.pull_full` | 每日 03:30 | 全天候 delta |
| `graph.push_event` | 用户编辑后 3s | outbox 回写 |
| `graph.reconcile` | 每日 04:00（P1） | 全窗口对账，发现幽灵/丢失则告警 |
| `sync.cleanup_tombstones` | 每日 04:30 | 删除 30 天前的软删记录（保留 `change_log` 水位） |
| `sync.cleanup_jobs` | 每小时 | 清理 done 状态 7 天前的任务 |
| `backup.daily` | 每日 02:00（由宝塔计划任务调 `backup.sh`） | mysqldump + rclone |
| `health.snapshot` | 每 5 分钟 | 记录 RSS / 队列深度 / 上次同步时间，写 `health_log` |

### 8.3 调度器实现约束

- `node-cron` 每分钟 tick 一次（不是每 30 秒扫全表，减少无谓查询）；
- 单 tick 最多领 3 个任务，总并发上限 2；
- 任务执行超 60s 强制中断并标 `pending` 重排（`attempts` 已 +1）；
- 进程重启时把 `running` 且 `locked_at` 超 5 分钟的任务重置为 `pending`（崩溃恢复）。

## 9. 内存预算与调优（2C2G 硬约束）

### 9.1 预算表

| 组件 | 常驻上限 | 说明 |
|---|---|---|
| 系统 + 现有其他服务 | 500 MB | 用户预留，含其宝塔上已有站点 |
| MySQL 8.0 独立实例 | 350 MB | buffer_pool 128M + performance_schema OFF |
| Node API（含调度） | 250 MB | `--max-old-space-size=256` |
| nginx（worker_processes 1） | 20 MB | 复用宝塔现有 nginx |
| 宝塔面板 | 200 MB | 已部分计入第一行，此处保守单列 |
| **合计** | **≈1.05~1.32 GB** | 2 GB 总量下留 680~950 MB |

**结论**：可行，但**必须**配 swap 并限死 Node 堆。

### 9.2 调优清单（逐条打勾）

```bash
# 1) swap（2G，仅作 OOM 缓冲，不指望性能）
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl -w vm.swappiness=10

# 2) Node 堆上限（写进 systemd unit，不靠环境变量）
#    ExecStart=/usr/bin/node --max-old-space-size=256 dist/index.js

# 3) nginx 单 worker
#    worker_processes 1; worker_connections 1024;

# 4) MySQL 按 §3.2 的 my.cnf

# 5) 宝塔面板：关闭「网站监控报表」「日志分析」等常驻插件
# 6) 关闭不用的 PHP-FPM 池（若本项目不用 PHP）
# 7) 限制日志：logrotate 14 天，journald SystemMaxUse=100M
```

### 9.3 升配触发条件（不要凭感觉）

出现任一条，即应升到 **2C4G**（或 4C4G）：

- swap 使用量连续 30 分钟 > 30%；
- `dmesg | grep -i "out of memory"` 出现任何一次；
- Node RSS 连续 1 小时 > 300MB；
- 每日 02:00~04:00 的备份/对账窗口内，API p95 延迟 > 1.5s。

### 9.4 M0 决策闸门

部署当天先执行：

```bash
free -m          # 看 available
systemctl status mysql-8.0   # 确认独立实例已起
ps aux --sort=-%mem | head -15
```

若 `available < 900 MB`（说明现有服务已占太多），**自动降级为"复用现有 5.7 建单库"**，并把所有统计查询改为应用层聚合；同时告知用户"内存是瓶颈，建议升配"。这一步必须在写业务代码前完成，避免后期返工。

## 10. 域名、HTTPS 与 nginx

### 10.1 DNS 与证书

| 项 | 值 |
|---|---|
| 子域 | `todo.<你的已备案域名>`（A 记录指向服务器公网 IP） |
| 证书 | 宝塔 Let's Encrypt，自动续期（提前 30 天） |
| 强制 | 80 → 301 到 443；HSTS `max-age=31536000; includeSubDomains` |
| TLS | 仅 1.2/1.3，禁用弱套件 |

### 10.2 nginx 关键配置

```nginx
server {
    listen 443 ssl http2;
    server_name todo.example.me;

    ssl_certificate     /www/server/panel/vhost/cert/todo.example.me/fullchain.pem;
    ssl_certificate_key /www/server/panel/vhost/cert/todo.example.me/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    # 安全头（CSP 与前端构建产物对应，含 inline-style 例外由 nonce 处理）
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Permissions-Policy "geolocation=(), camera=(), microphone=()" always;

    root /www/wwwroot/todo/apps/web/dist;
    index index.html;

    # 静态资源长缓存（文件名带 hash）
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # SPA 回退
    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache";
    }

    # API 反代
    location /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 90s;
        client_max_body_size 2m;
    }

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;
}
```

> `/api/oauth/microsoft/callback` 必须走 HTTPS 且公网可达，否则微软会拒绝注册该重定向 URI。

## 11. 部署流程（用户在宝塔执行）

```bash
# 0) 一次性：装 Node 24（不影响现有 Node 20 站点）
#    宝塔「Node 版本管理器」安装 v24，或 nvm install 24
node -v   # 期望 v24.x

# 1) 拉代码
cd /www/wwwroot && git clone <repo> todo && cd todo
pnpm install --frozen-lockfile

# 2) 配置环境变量
cp deploy/env.example .env && vim .env
#   DATABASE_URL=mysql://grid_rw:***@127.0.0.1:3307/grid
#   TOKEN_ENC_KEY=<openssl rand -base64 32>
#   SESSION_SECRET=<openssl rand -base64 32>
#   MS_CLIENT_ID / MS_CLIENT_SECRET / MS_REDIRECT_URI
#   APP_BASE_URL=https://todo.example.me

# 3) 建表
pnpm --filter server db:migrate
pnpm --filter server seed:user --email you@x.com --password '...'

# 4) 构建
pnpm --filter web build
pnpm --filter server build

# 5) 起服务
cp deploy/grid.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now grid
systemctl status grid

# 6) 反向代理
#    宝塔新建站点 todo.example.me → 按 deploy/nginx.conf.example 填 → 申请 SSL

# 7) 验证
curl -s https://todo.example.me/api/healthz | jq
```

### 11.1 systemd unit

```ini
[Unit]
Description=GRID API
After=network.target mysql-8.0.service

[Service]
Type=simple
User=www
WorkingDirectory=/www/wwwroot/todo/packages/server
EnvironmentFile=/www/wwwroot/todo/.env
ExecStart=/usr/bin/node --max-old-space-size=256 dist/index.js
Restart=always
RestartSec=3
MemoryMax=380M
MemoryHigh=320M

# 安全加固
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ReadWritePaths=/www/wwwroot/todo
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

`MemoryMax` 是最后一道保险：超过 380M 直接被 cgroup 杀掉并重启，而不是拖死整台机器。

> **实施注记**（实测于 CentOS 7 / systemd 219）：`MemoryMax` / `MemoryHigh` 是 systemd 231
> 才引入的字段，219 上要写 `MemoryLimit` / `MemorySoftLimit`。而在 cgroup v1 未启用
> memory controller 的老内核上，即使字段名对了也只会得到一条
> `Invalid memory limit ..., ignoring: Invalid argument (-22)` —— 服务照常运行，
> 但这层保险实际不存在。这类机器建议直接注释掉，靠 `--max-old-space-size`
> 与 swap 兜底；细节见 `09-部署手册.md` §6.1。

## 12. 日志、监控与告警

### 12.1 日志

| 项 | 策略 |
|---|---|
| 库 | pino，JSON 单行 |
| 分级 | prod `info`（错误 `error`），dev `debug` |
| 落盘 | pino-roll，按日切割，保留 14 天，单文件 20M |
| 脱敏 | `redact: ['req.headers.cookie','req.headers.authorization','*.password','*.access_token','*.refresh_token','*.code_verifier']` |
| 请求日志 | 记录 `method/path/status/duration/req_id`，**不记录 body** |
| 关联 | 每个请求生成 `req_id`，Graph 调用日志带上同一 `req_id`，便于串链路 |

### 12.2 监控

- **`GET /api/healthz`** 返回：`{ ok, db: 'up|down', queue: {pending, dead}, lastSyncAt, rssMB, uptime }`
- 外部可用 Uptime Kuma（自托管，另占约 80MB；若内存紧则用宝塔「网站监控」+ 定时 curl）每 5 分钟探活，连续 3 次失败发邮件/企微。
- `health_log` 表每 5 分钟一条，用 SQL 出趋势：RSS 曲线、队列深度、同步延迟。

### 12.3 备份与恢复

```bash
#!/usr/bin/env bash
# deploy/backup.sh
set -euo pipefail
STAMP=$(date +%F_%H%M)
DEST=/www/backup/grid
mkdir -p "$DEST"
mysqldump -h127.0.0.1 -P3307 -ugrid_rw -p"$DB_PASS" \
  --single-transaction --quick --routines --triggers --set-gtid-purged=OFF \
  grid | gzip -9 > "$DEST/grid_$STAMP.sql.gz"

# 本地保留 7 日 + 4 周
find "$DEST" -name 'grid_*.sql.gz' -mtime +7 -not -name '*week*' -delete

# 异地（对象存储）
rclone copy "$DEST/grid_$STAMP.sql.gz" oss:grid-backup/daily/ --bwlimit 2M
```

- 宝塔「计划任务」每日 02:00 调用；
- 每周日额外 `cp` 一份到 `weekly/`，保留 4 份；
- **恢复演练（每季度一次，必须真做）**：
  ```bash
  gunzip < grid_2026-11-23_0200.sql.gz | mysql -h127.0.0.1 -P3307 -ugrid_rw -p grid
  ```
  验证 `SELECT COUNT(*) FROM task` 与线上一致。

## 13. 服务器配置结论

| 项 | 最低可用 | 推荐 |
|---|---|---|
| CPU | 2 核 | 2 核 |
| 内存 | 2 GB + 2 GB swap（需严格按 §9 调优） | **4 GB**（跨过 OOM 焦虑，成本差异很小） |
| 磁盘 | 40 GB SSD | 60 GB SSD（备份本地副本 + 日志） |
| 带宽 | 3 Mbps | 5 Mbps |
| 系统 | Ubuntu 22.04 / Debian 12 | 同 |
| 软件 | Node 24 LTS、MySQL 8.0（独立实例）、nginx、rclone | 同 + Uptime Kuma（可选） |

**坦率建议**：2C2G 能跑，但你的服务器上已有其他重要服务，任何一次内存尖峰都可能连带影响别人。如果这台的定位是"主力生产"，加到 4G 是性价比最高的一笔投入；如果坚持 2G，就严格按 §9 执行，且接受"备份窗口内可能变慢"。

## 14. 架构层面的已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| MySQL 8.0 已 EOL | 无安全补丁 | 只绑 127.0.0.1 + 专用低权账号 + 定期离线备份 |
| 单进程模型 | 同步任务可能拖慢 API | 并发限 2 + 超时 60s + 预留 `WORKER_MODE` 拆分开关 |
| 个人 MSA 无 app-only 流 | 令牌失效后同步静默停摆 | 红色通栏 + 最近刷新时间可见 + 一键重授权 |
| Graph 不支持 EXDATE | 重复事件无法 100% 等价 | P0 只读；P1 投影 + 夜间对账 |
| 2C2G 零余量 | OOM 风险 | swap + MemoryMax + 升配触发条件 |
| 无实时推送 | 另一端改动最多 60s 后才可见 | 可接受；预留 SSE 路由位 |
