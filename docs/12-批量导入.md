# 12 · 批量导入任务

> 入口：网页版 → 设置 → 批量导入任务。下载模板 → 填 → 上传 → 预览 → 导入。

---

## 1. 为什么是 CSV 而不是 xlsx

xlsx 的读取需要一个解析库（SheetJS 完整包 ~1MB），而 CSV 只需要 120 行解析代码。
更关键的是：**xlsx 会让人以为"格式可以随便"**——合并单元格、公式、多 sheet、隐藏行，
每一样都得决定"导入时算哪个"。CSV 只有一张表，没有这些歧义。

代价是 Excel 用户要点一次「另存为 CSV」，这一步省不掉，但换来的是导入行为可预测。

## 2. 十一列

| # | 列名 | 填法 | 必填 |
|---|---|---|---|
| 1 | 标题 | 文本，≤512 字 | ✅ |
| 2 | 日期 | `2026-12-01` | |
| 3 | 时间 | `09:30`，留空 = 全天任务 | |
| 4 | 结束时间 | `10:30`，留空 = 不设结束 | |
| 5 | 象限 | `01`–`04` 或 1–4，留空按 04 | |
| 6 | 优先级 | 无/低/中/高 或 0–3 | |
| 7 | 标签 | 用**分号**分隔，不存在的自动新建 | |
| 8 | 地点 | 文本，≤256 字 | |
| 9 | 备注 | 文本，≤1 万字 | |
| 10 | 提醒提前 | 分钟数，`15` = 提前 15 分钟 | |
| 11 | 重复 | 见下表 | |

表头**认别名**：`title` / `due` / `tags` / `prio` 这些英文列名也能识别，方便从别的工具直接搬。

### 重复列的档位

| 写法 | 生成 | 备注 |
|---|---|---|
| `每天` | `FREQ=DAILY` | |
| `工作日` | `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR` | |
| `每周三` | `FREQ=WEEKLY;BYDAY=WE` | 一到日都认 |
| `每月15号` | `FREQ=MONTHLY;BYMONTHDAY=15` | 指定几号 |
| `每月` | `FREQ=MONTHLY;BYMONTHDAY=<日期列的日>` | 取日期列 |
| `每年` | `FREQ=YEARLY` | 取日期列的月日 |

**「每年 3 月 5 日」这种写法不支持**，原因是 core 的 RRULE 实现里 `SUPPORTED_KEYS`
没有 `BYMONTH`（`packages/core/src/recurrence/rrule.ts`）。想表达它，就让日期列写 `2026-03-05`
再在重复列写「每年」。

## 3. 三条行为约定

**① 整批失败 = 一条都不写。**
校验阶段收齐所有错误一起报（不是遇到第一个就停），有任何一个错误就不允许点导入。
点下去之后是**一个 Dexie 事务**，中途任何异常都会整体回滚。

为什么强调"不是靠预先检查"：检查只能挡住格式错误，挡不住写入时磁盘配额满、
另一个标签页把库锁住这类事故。没有事务的话，那种失败会留下"前 300 条在、后 200 条没在"，
而这恰好是用户最难处理的状态——不知道从哪继续，也不知道重导会不会重复。

**② 标题 + 日期相同就跳过。**
同一份文件导两次不会变成两份。不用标题单独判：同一件事在月初月末各做一次很常见。
也不用标题 + 时间：全天任务没有时间，"上午想到又加一遍"应该被挡住。

**③ 单次上限 2000 条。**
2000 条的 `bulkAdd` 在一个事务里约 1–2 秒，界面会卡一下但能接受。
上万条时事务持有时间过长，浏览器可能判定页面假死。超限会直接拒绝并提示拆批。

## 4. 三个实现陷阱（都已处理）

### 4.1 `new Date('2026-12-01')` 是 UTC 午夜

```
new Date('2026-12-01')              → 2026-12-01T00:00:00Z  → 东八区是 08:00
new Date('2026-12-01T00:00:00')     → 2026-12-01T00:00:00   → 本地午夜，正确
```

CSV 的「日期 + 时间」要合成时间戳，必须显式拼 `T00:00:00`。
用错的话，填 `09:30` 会导入成 `17:30`，而且**在 UTC+0 的机器上完全测不出来**。
同理「每月」取日期列的天数时，直接从字符串 `slice(8, 10)`，不要过 Date。

### 4.2 Excel 另存的 CSV 是 GBK

中文 Windows 上 Excel 默认存 GBK，而 `FileReader` / `TextDecoder` 默认按 UTF-8 读，
结果是满屏乱码，用户会以为"下载的模板是坏的"。

处理顺序：先按 UTF-8 **严格**解码（`fatal: true`，遇到非法字节直接抛），失败再退回 GBK。
反过来做不行——GBK 解码几乎不会失败，会把 UTF-8 的中文解成乱码却不报错。

导出的模板带 BOM，Excel 双击打开才不会乱码。

### 4.3 `bumpHlc()` 会在事务里再开事务

`apps/web/src/sync/hlc.ts` 的 `bumpHlc()` 自己调用 `db.transaction('rw', db.meta, …)`。
如果把批量导入整个包在一个大事务里、再逐条调它，Dexie 会抛嵌套事务错误。

做法：事务**外**先取一枚基准 HLC，事务内按 `counter + i` 递增，最后把水位写回 `meta`。
这符合 HLC 的定义（墙钟相同则计数递增），不会破坏任何排序假设。

## 5. 验收

```bash
cd packages/server && ./node_modules/.bin/tsx ../../tools/import-check.ts
```

31 条断言，覆盖：模板自身可用、引号内逗号/换行/双引号、BOM、八类校验错误与行号、
六种重复档位、英文表头别名、以及那条 UTC 时区陷阱。

浏览器侧还需要手动确认的四点：

| # | 动作 | 期望 |
|---|---|---|
| 1 | 下载模板 → Excel 打开 | 中文不乱码，4 行（表头 + 2 示例 + 空行） |
| 2 | 直接在 Excel 里另存为 CSV 再上传 | 不报乱码，能解析出 2 条 |
| 3 | 故意改坏一行的日期 | 预览区红框列出「第 N 行 … 不是合法的 YYYY-MM-DD」，导入按钮不可点 |
| 4 | 导入 3 条 → 立即再导同一份 | 第一次"新增 3 条"，第二次"新增 0 条，跳过 3 条" |

## 6. 已知限制

| 限制 | 原因 |
|---|---|
| 不支持父子任务 | CSV 里表达层级要么写父标题再匹配（重名就错），要么用缩进（Excel 里看不见）。这一版不做 |
| 导入的都在收件箱 | 现在只有一个清单（`list-inbox`），没有建清单的入口 |
| 不导入「已完成」状态 | 保持 11 列，导进来的都是未完成任务 |
| 手机端没有导入入口 | 手机上选文件和存文件的体验都不好，这类操作放网页版更合适 |
