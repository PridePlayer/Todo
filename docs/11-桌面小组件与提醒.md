# 11 · 桌面小组件与本地提醒

> 现状：小组件的读、写、刷新三条链路已接完，后端接口与权限隔离已跑过验收脚本。
> 本地提醒见文末「未完成」——它缺的是设置入口，不是排程能力。

---

## 1. 为什么这件事必须出 APK

`react-native-android-widget` 是原生模块。Expo Go 里没有它，加载到 `registerWidgetTaskHandler`
那一步就会抛 `NativeModule is null`。

所以这一步把 M6 里"等界面定稿再出 APK"的顺序**提前**了。代价要认：

| 方式 | 一次改动到看到效果 |
|---|---|
| Expo Go（改 JS） | 秒级热更 |
| 本仓库现状（无本地 Android SDK） | `eas build` 云构建 10–20 分钟 |
| 装本地 SDK（JDK 17 + Android SDK） | `expo run:android` 热更，但一次性要下 3–5GB |

## 2. 4×4 的排版规格

一块约 250dp 见方，扣除内边距后可用约 224dp。**待办 3 行 + 打卡 3 行，两块面积对等**：

```
今天 · 11 月 25 日 周三          未完成 5
─────────────────────────────────────
▍○ 交周报草稿                  逾期
▍○ 看第三章
▍○ 回复邮件
─────────────────────────────────────
打卡                        连续 12 天
○ 喝水                            3/8
● 阅读                            1/1
○ 跑步                            0/5
```

| 位置 | 内容 | 约束 |
|---|---|---|
| 右上角 | `未完成 N`（N = 逾期 + 今日，**不含收件箱**） | 与 App 首屏同一个数字 |
| 待办 | 最多 3 行，每行 31dp | 接口返回 4 条，第 4 条用于补位 |
| 打卡 | 最多 3 行，每行 27dp | 超出显示「还有 N 个打卡项」 |
| 打卡圆 | 实心蓝 = 已达标、蓝边 = 点过未达标、灰边 = 未动 | 见下方「为什么不是打勾」 |

**为什么打卡不是"一行四个圆点"**：第一版就是这样，结果用户不知道哪个圆是哪个习惯、
点了没到目标还以为点击失灵。省下来的空间全变成了理解成本，所以改成和待办同一个语法
（左边一个圆、中间名字、右边数字），占用面积也对等地给了三行。

**为什么进度数字必须有**：计数型目标 8 杯水，喝到 3 杯时圆是"蓝边"而不是"实心"，
如果只显示打勾/不打勾，用户点了三下看到毫无变化，就会认定这个按钮坏了。

刻意没做的四件事：

1. **不做尺寸自适应**：`resizeMode: "none"`，拉不动。做自适应要四套布局，第一次构建验证不完。
2. **固定浅色**：App 的 `userInterfaceStyle` 就是 `light`；库的 dark mode 是另一套尺寸表。
3. **不带日程**：砍掉之后待办和打卡才能各占三行。
4. **打卡不可撤销**：桌面上误触概率高，而 widget 上没有撤销提示可给。

## 3. 令牌：为什么有两把

| 令牌 | 存在哪 | 能做什么 |
|---|---|---|
| 主设备令牌（`scope='full'` 或 NULL） | SecureStore | 全部接口，180 天，临期静默轮换 |
| 小组件令牌（`scope='widget'`） | **sqlite 的 `meta` 表（明文）** | 只能读 `/api/widget/summary`，90 天，不轮换 |

分两把的理由只有一个：**headless JS 能不能解开 SecureStore 是未知数**。

那个上下文没有 UI、没有 Activity 的引用，Keystore 解密是否可用要看实现。
如果不可用而只有主令牌，小组件就彻底空白；有一把明文的**只读**令牌，
最坏情况也只是"今天有哪几条待办"被人看到，而不是整个账号。

三处配套的纪律：

- `requireUser()` **默认拒绝** widget 令牌。它是白名单式放行，不是黑名单式拦截 ——
  以后新增任何路由都自动对 widget 令牌关闭，而黑名单写法会静默多开一扇门。
- `POST /devices/rotate` 显式挡 widget 令牌：那里签的是 full 令牌，放行就等于一步提权。
- 签发新 widget 令牌时先吊销旧的。App 每次启动都可能续签，不吊销会在表里堆一串都能用的令牌。

## 4. 数据流

```
WIDGET_ADDED / UPDATE / RESIZED
  └─ loadWidgetSummary()
       ├─ 有 widget 令牌 → GET /api/widget/summary → 写缓存 → 画
       ├─ 没有 → 退回 SecureStore 主令牌 → 同上
       └─ 都失败 → 读 sqlite 缓存（带日期校验）→ 画；连缓存都没有 → "打开 App 登录"

WIDGET_CLICK (TOGGLE_TASK / CHECK_HABIT)
  ├─ 读本地镜像拿完整行（摘要只有渲染字段）
  ├─ domain/toggle.ts 写入 outbox（乐观）
  ├─ 立刻重绘（这条消失、下一条补上来）—— 不等网络
  └─ 后台 pushOutbox()，失败留着下次推
```

**缓存为什么要校验日期**：昨天的三条待办出现在明天的桌面上，比一片空白更糟 ——
用户会以为那就是今天的。

**为什么刷新是"先远端、失败回缓存"**：待办这个场景里过期数据会误导人
（看着"3 条未完成"，其实早做完了）。缓存只在拿不到数据时兜底。

### 必须消费 push 响应里的 `serverPayload`

这一条是踩出来的：服务端对打卡值是 `GREATEST(local, remote)`、对标签取并集、
对四象限整块裁决 —— 也就是**推上去的值经常不等于最终生效的值**。

```
手机 value=1 推上去 → 服务端已有 2 → merge 保留 2 → 该行 change_seq 不变
→ 之后 pull 用 `change_seq > cursor` 拉不到这行 → 手机永远显示 1/2
```

"永远"是真的永远，不是等一会儿会自愈。修复方式是 `apps/mobile/src/sync/push.ts`
在收到 `serverPayload` 时用 `applyServerPayload()` 覆盖本地行（Web 端一直是对的，
只有手机端漏了这段）。

已经错位的数据不会因为改了代码而自动对齐（那次 push 早已成功、outbox 已空），
所以设置页有一个「重新拉取全部数据」：先 flush 把待推的推干净，再清空本地、游标归零、
全量 pull。它只在"两端数字对不上且怎么同步都不变"时用。

## 5. 构建与安装

```bash
# 一次性：装 CLI（包名是 eas-cli，不是 eas —— `npx eas` 会找到同名占位包并报
# "could not determine executable to run"，这个报错和网络、权限都没关系）
npm i -g eas-cli

cd apps/mobile

# 首次需要先登录（浏览器弹窗，一次性）
eas login

# 出 APK（profile=preview，distribution=internal）
eas build -p android --profile preview

# 构建完成后下载链接会打印出来，手机浏览器打开即可安装
```

不想全局安装的话，把上面两条 `eas ...` 换成 `npx eas-cli@latest login` /
`npx eas-cli@latest build -p android --profile preview`，代价是每次都要检查版本。

`app.json` 里已有 `versionCode` 自增（`eas.json` 的 `autoIncrement: true`），不用手动改。

装好后：长按桌面 → 小组件 → 找到「GRID 今天」→ 拖到桌面。
**注意**：4×4 是 `targetCellWidth/Height`，桌面网格小于 4×4 的 launcher 会拒绝添加。

### 装到手机上之后的七条
| # | 动作 | 期望 | 不通过的典型症状 |
|---|---|---|---|
| 1 | 拖一个「GRID 今天」到桌面 | 出数据，数字与 App 首屏一致 | 一片空白 → headless 任务没注册或 sqlite 打不开 |
| 2 | 点一条待办 | 立刻消失，下一条补上来 | 点了没反应 → `renderWidget` 没被调用 |
| 3 | 上一步之后看服务器 | `task` 该行 `completed_at` 有值 | 本地变了、服务器没变 → headless 读不到主令牌 |
| 4 | 点一个打卡点，再点一次 | 第一次变实心；第二次**没有变化** | 第二次变空心 → "只打不撤"没生效 |
| 5 | 断网后点一条待办 | 桌面上照样消失 | 不消失 → 乐观更新依赖了网络 |
| 6 | 联网后打开 App | 设置页「待推」归零，那条约待办在服务器上是已完成 | 归零但服务器没变 → deviceId 变了，服务端当成另一台设备 |
| 7 | 等 30 分钟不动手机 | 小组件自己刷新一次 | 一直不刷新 → `updatePeriodMillis` 没进 provider XML |

第 6 条是最容易静默失败的一条：`ensureDeviceId()` 在 headless 里如果读不到 SecureStore，
会**现生成一个新的 deviceId**，服务端从此把同一台手机记成两台设备。
冲突日志里会全是"自己和自己冲突"，但界面上一切正常。

## 7. 已知限制

| 限制 | 原因 | 能不能解 |
|---|---|---|
| 最快 30 分钟刷新一次 | Android 的 `updatePeriodMillis` 下限 | 不能。想更实时只能靠点击或 App 内 `requestWidgetUpdate` |
| 跨零点后最多 30 分钟才换天 | 同上 | 要精准 0 点刷新得挂 AlarmManager，本库不提供 |
| 拉成 4×2 会留白 | `resizeMode: "none"` | 要做就写四套布局 |
| 打卡点了不能撤 | 产品决定（见 §2） | 能，但要先设计误触保护 |
| iOS 没有 | 项目只做 Android + Web | 需要 Mac + Xcode 重写一套 WidgetKit |

## 8. 本地提醒

两条链路都接了，PRD 的 `T-01` 与 `H-07`：

| 类型 | 存什么 | 锚点 | 在哪儿设 |
|---|---|---|---|
| 任务提醒 | `task.remind_lead_minutes`（提前多少分钟） | 有 `startAt` 用它，否则 `dueDate` 当天 09:00 | App 任务详情 → 提醒 |
| 打卡提醒 | `habit.remind_minute`（一天中的第几分钟） | 每天固定时刻 | Web 习惯详情 / 新建表单；App 只读 |

### 为什么任务存"提前量"而不是"提醒时刻"

已有的 `task.remind_at` 是绝对时间戳，**保留但不再写入**。原因：用户在界面上选的是
「提前 15 分钟」，如果落库存成绝对时间，任务一改期提醒就停在旧时间上 ——
而"改了会议时间，提醒还在昨天响"这种错误，没有任何界面能看出来。
存相对量则锚点一变、提醒自动跟着走，三端都不需要记得重算。

### 排程策略

`src/notify/schedule.ts`：

- **每次全取消再全排**，不做增量。增量更新要维护"哪条通知对应哪个任务"的映射，
  而这个映射在应用被系统杀掉、数据被另一台设备改过之后必然对不上。
  几百条规模下全量重排是几十毫秒，换来"绝不会出现两条重复通知"。
- **只排未来 7 天**。再远的时间点，等用户下次打开 App 重排更准（任务大概率会改期）。
- **30 秒内要响的跳过**：排完就响，用户会以为是 bug。
- **数据指纹去重**：每次同步都会调 `reload()`，但提醒条目的 id + 时间没变就直接返回，
  不会反复调原生接口。
- 退出登录调 `cancelAllReminders()`。不清的话，换账号后会收到上一个人的待办标题。

### 三条权限

第一次在任务详情里选提醒时会自动弹引导（`src/notify/PermissionGuide.tsx`），
设置页也有「检查提醒权限」入口。三步都可跳过：

1. **通知权限** —— 能直接用 `requestPermissionsAsync` 请求，这一条能真办到
2. **精确闹钟**（Android 12+）—— 特殊权限，JS 打不开，只能 `Linking.openSettings()` 送过去
3. **电池白名单** —— 同上。小米/华为/OPPO/vivo 熄屏后冻结后台，提醒就再也不响

`app.json` 已声明 `SCHEDULE_EXACT_ALARM`、`USE_EXACT_ALARM`、`RECEIVE_BOOT_COMPLETED`。
第三条（白名单）没有任何 API 能查状态，所以引导里那两步只能标"去设置"、无法标"已完成"。

### 已知限制

| 限制 | 原因 |
|---|---|
| 重启后提醒依赖系统行为 | `RECEIVE_BOOT_COMPLETED` 已声明，但国产 ROM 可能仍需要白名单 |
| 打卡提醒在桌面端只读 | 手机上「新建习惯」还没做（docs/10 §7），所以只能在 Web 设 |
| 用户在系统里关掉的通知，下次重排会重新出现 | 我们能控制的只有排程，控制不了系统通知开关 |
