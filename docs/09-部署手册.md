# 09 · 部署手册（todo.stellamp.me）

> 目标环境：阿里云 ECS + 宝塔面板 + nginx + systemd + MySQL 5.7。  
> 本文按"照着敲就能上线"的顺序写，每一步都有**验证命令**和**失败时看哪里**。
>
> 一次性做完 0–8，之后每次更新只需第 9 节的一条命令。

## 0. 先花五分钟看清现状

在服务器上执行，把结果对照右边一栏：

```bash
node -v; pnpm -v; nginx -v; mysql --version
free -m | head -2
df -h / | tail -1
systemctl list-units --type=service | grep -c grid   # 应为 0，说明还没起过
```

| 项    | 要求                     | 不满足会怎样                             |
| ---- | ---------------------- | ---------------------------------- |
| Node | **≥ 22.12**（推荐 24 LTS） | 服务起不来 + 前端构建失败，见 1                 |
| pnpm | ≥ 9（本地用 10.34）         | `--frozen-lockfile` 报 lockfile 不兼容 |
| 内存   | ≥ 1 GB 可用              | 构建时被 OOM 杀掉（`Killed`）              |
| 磁盘   | ≥ 2 GB 可用              | 构建中途 `ENOSPC`                      |

> **你现在的 Node 是 v20.9.0，第 1 步必须做，否则一定失败。**  
> 这个项目的 `engines` 写的是 `>=22.12`：Vite 8 的构建链路要 20.19+/22.12+，  
> 服务端也依赖 Node 22 的若干内置能力。

## 1. 升级 Node

### 方案 A：宝塔「Node 版本管理器」（与现有面板一致，推荐）

1. 宝塔 → 软件商店 → 搜「Node.js 版本管理器」→ 安装
2. 打开 → 版本列表 → 选 **v22.22.0 LTS**（或 24.x）→ 安装
3. 记下安装路径，形如 `/www/server/nodejs/v22.22.0/bin/node`
4. 把这个目录加进全局 PATH（**不要**替换系统的 `/usr/bin/node`，这台机器上还有 yalta / holmes / gcx-api 在跑）

```bash
echo 'export PATH=/www/server/nodejs/v22.22.0/bin:$PATH' >> ~/.bashrc
source ~/.bashrc
node -v          # 期望 v22.22.0
npm i -g pnpm@10
pnpm -v          # 期望 10.x
```

### 方案 B：nvm

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
source ~/.bashrc
nvm install 22 && nvm use 22 && nvm alias default 22
npm i -g pnpm@10
```

**验证**

```bash
which node && node -v && which pnpm && pnpm -v
```

> 注意：方案 A/B 只影响**登录 shell**。第 6 步的 systemd unit 里 `ExecStart` 必须写**绝对路径**，  
> 因为 systemd 不读 `~/.bashrc`。

## 2. 建库与账号（MySQL 5.7，宝塔面板做法）

项目按 5.7 可移植写的（不用 JSON 列 / 窗口函数 / CTE / `ON DUPLICATE KEY`），  
**直接用现有 5.7 实例即可**，不必为它再起一个 8.0。

### 2.1 面板上点六下

宝塔面板 → 左侧「数据库」→「添加数据库」：

| 字段   | 填什么                     | 说明                                    |
| ---- | ----------------------- | ------------------------------------- |
| 数据库名 | `grid`                  | 全小写，别加前缀                              |
| 用户名  | `grid_rw`               | 不要用 root，不要用库名当用户名（后面排错时看不出是谁在连）      |
| 密码   | **只用大小写字母 + 数字，24 位以上** | 见下面 2.2，这一步决定了你后面会不会卡在 URL 解析上        |
| 权限   | **本地服务器**               | 不要选「所有人」；选它等于把库开放给任何能连到 3306 的地址      |
| 字符集  | `utf8mb4`               | 没有这个下拉就建完再按 2.3 检查，**utf8 存不了 emoji** |
| 备注   | `GRID 待办`               | 可选，方便以后认                              |

点「提交」。宝塔会同时把这个库和这个账号建好并授权。

### 2.2 密码为什么必须只含字母数字

`DB_URL` 是一个 URL：

```
mysql://grid_rw:密码@127.0.0.1:3306/grid
```

密码里出现 `@`、`:`、`/`、`#`、`?` 任何一个，都会被解析成分隔符 ——  
`@` 会被当成"主机开始"，`#` 后面整段被当锚点丢掉。症状是服务启动报  
`数据库连不上`，但你明明在 phpMyAdmin 里用同一个密码能登录。

宝塔默认的「随机」按钮会生成带符号的密码，**点它生成的密码不要直接用**，  
自己敲一串字母数字（比如 `Gr1dTodo2026Xk9mQp7vLz3`），或者生成后手改。

另注：`TOKEN_ENC_KEY` 正相反——那个必须是 base64 带符号的随机串，见第 4 节。两者别混。

### 2.3 建完检查两件事

在宝塔「数据库」列表里点 `grid` 那一行的「管理」，会打开 phpMyAdmin（root 已登录），  
全程不用连 SSH：

**第一，字符集**。左侧点 `grid` → 「操作」标签 → 看「排序规则」：

- `utf8mb4_general_ci` 或 `utf8mb4_unicode_ci` → 都行，项目没依赖具体排序规则
- `utf8_general_ci`（没有 mb4）→ **改掉**：同一个「操作」页最下面「修改所有表」里选 `utf8mb4_unicode_ci`，或者干脆删库重建并确认字符集下拉选对

**第二，行格式**。phpMyAdmin → 「SQL」标签 → 执行：

```sql
SELECT @@innodb_large_prefix, @@innodb_default_row_format;
```

期望看到 `1` 和 `dynamic`。如果 `dynamic` 显示成 `compact`，  
后面第 5 步 `db:migrate` 建 `app_user.email` 唯一索引时会报  
`Specified key was too long; max key length is 767 bytes` ——  
原因见下面 2.4 的说明。

### 2.4 两个 5.7 相关的坑

**坑一：邮箱唯一索引超长。**  
`app_user.email` 是 `VARCHAR(255)` 且带唯一索引，utf8mb4 下一个字符最多 4 字节，  
算下来 1020 字节，超过旧行格式的 767 上限。5.7 默认是 `DYNAMIC` + 大前缀，不触发；  
只有从 5.6 升上来、或被人手动改过 `row_format` 的实例才会撞上。

**坑二：`localhost` 与 `127.0.0.1` 不是同一个 host。**  
权限选「本地服务器」时，宝塔创建的是 `'grid_rw'@'localhost'`；  
而 `DB_URL` 里写的是 `127.0.0.1`，走的是 TCP。MySQL 是否把两者当同一个人，  
取决于有没有开 `skip-name-resolve`。

如果第 5 步报 `Access denied for user 'grid_rw'@'127.0.0.1'`，去 phpMyAdmin 的「SQL」页执行一次：

```sql
GRANT ALL PRIVILEGES ON grid.* TO 'grid_rw'@'127.0.0.1' IDENTIFIED BY '你在面板里设的同一个密码';
FLUSH PRIVILEGES;
```

（5.7 支持 `GRANT ... IDENTIFIED BY`；8.0 不支持，那时要改成先 `CREATE USER` 再 `GRANT`。）

> 顺带一提：`127.0.0.1` 只在本机生效，公网连不进来，所以这条授权没有扩大暴露面。

### 2.5 备选：命令行一次性建好

不想点面板的话，root 登录后整段执行（密码记得换成字母数字）：

```sql
CREATE DATABASE grid
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

CREATE USER 'grid_rw'@'127.0.0.1' IDENTIFIED BY '换成24位字母数字';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES
  ON grid.* TO 'grid_rw'@'127.0.0.1';
FLUSH PRIVILEGES;
```

**验证连通**（两边等价，选一个）

```bash
# 命令行
mysql -h127.0.0.1 -P3306 -ugrid_rw -p'密码' grid -e 'SELECT 1'

# 或者交给第 5 步：migrate 能跑通就说明账号权限全都对
cd /www/wwwroot/todo && pnpm --filter @grid/server db:migrate
```

## 4. 配 .env

```bash
cd /www/wwwroot/todo
cp deploy/env.example .env
openssl rand -base64 32          # 生成 TOKEN_ENC_KEY，先复制出来
vim .env
```

必须逐项确认的五个值：

| 变量                | 值                                                       | 写错的后果                                                                     |
| ----------------- | ------------------------------------------------------- | ------------------------------------------------------------------------- |
| `DB_URL`          | `mysql://grid_rw:密码@127.0.0.1:3306/grid`                | 密码必须只含字母数字（见 2.2）。含 `@ : / #` 会被 URL 当分隔符切开，症状是「明明 phpMyAdmin 能登，服务却说连不上」 |
| `APP_ORIGIN`      | `https://todo.stellamp.me`                              | 少 https 或多斜杠 → 登录 403 `csrf_failed`                                       |
| `COOKIE_SECURE`   | `true`                                                  | `__Host-` 前缀的 Cookie 非 Secure 会被浏览器直接丢弃 → 登录后立刻掉线                         |
| `TOKEN_ENC_KEY`   | 上面生成的 44 字符                                             | 为空 → 存 MS 令牌时报错；**上线后再改这个值会让已存的令牌全部无法解密，需要重新授权**                          |
| `MS_REDIRECT_URI` | `https://todo.stellamp.me/api/oauth/microsoft/callback` | 与 Azure 里注册的必须逐字符一致，否则 `AADSTS50011`                                      |

```bash
chmod 600 .env          # 里面有数据库密码和 MS 客户端密码
```

Azure 侧同步改一次：门户 → 应用注册 → 认证 → 重定向 URI 加  
`https://todo.stellamp.me/api/oauth/microsoft/callback`（Web 类型）。

## 6. systemd 服务

```bash
cp deploy/grid.service /etc/systemd/system/grid.service
vim /etc/systemd/system/grid.service
```

要改两处（其余保持原样）：

```ini
# 1) 换成第 1 步记下的绝对路径，systemd 不走 PATH
ExecStart=/www/server/nodejs/v22.22.0/bin/node --max-old-space-size=256 dist/index.js

# 2) After= 里的 MySQL 服务名按实际改，不确定就整行注释掉
# After=network.target mysql-8.0.service
After=network.target
```

**第 3 处（内存上限）默认是注释掉的，不用管。** 想要"泄漏时自动重启"这层兜底再打开，字段名按版本选：

| systemd 版本 | 典型系统 | 写法 |
|---|---|---|
| 219 | CentOS 7、阿里云老镜像 | `MemoryLimit=512M`（`MemoryMax` 是 231 才有的名字） |
| ≥ 231 | Alibaba Cloud Linux 3、CentOS 8+、Ubuntu 20.04+ | `MemoryMax=512M` |

> **实操结论：老机器上直接留注释就好。**
> 实测 CentOS 7 / systemd 219 + cgroup v1 未启 memory controller：字段名写对、服务也正常 active，
> 但每次 `daemon-reload` 都多一条
> `grid.service:21: Invalid memory limit 536870912, ignoring: Invalid argument (-22)`
> （`-22` = `EINVAL`，内核拒绝了这次写入）。它不影响运行，只是刷日志、
> 且 `systemctl status` 里的 `Memory:` 那一行永远不准。为它去改内核 cgroup 参数不划算。

### 6.1 起不来时：先看 journal 的上一行

`systemctl start grid` 失败时那句话很容易把人带偏：

```
Job for grid.service failed because of unavailable resources or another system error.
```

`systemctl status` 里也只有：

```
Active: activating (auto-restart) (Result: resources)
```

**`result 'resources'` 是个垃圾桶**：systemd 把"启动准备阶段失败"全都塞进这一类，
`EnvironmentFile` 读不到、`WorkingDirectory` 不存在，都算 `resources`。
真正的原因在 journal 里，永远在 `Failed with result` 的**上两行**：

```bash
journalctl -u grid.service -n 30 --no-pager
```

| journal 里的那一行 | 原因 |
|---|---|
| `Failed to load environment files: No such file or directory` | `.env` 不存在（没做第 4 步，或 `EnvironmentFile` 路径不对） |
| `Failed to run 'start' task: No such file or directory` | `WorkingDirectory` 不存在，或 `ExecStart` 里的 node / `dist/index.js` 路径不对 |
| `Failed to determine user credentials` | `User=www` 这个用户不存在 |
| `Failed to set up output file` | 日志目录没建（见下面这条命令） |

**排查顺序**：先 `journalctl` 看那一行 → 按上表对号 → **不要**先去调 `MemoryMax`。
（这个错误我本人踩过一次：`.env` 没建，我误判成内存限制，改了两轮字段都没用。）

```bash
# 建日志目录：漏了这一步不会提示"目录不存在"，而是 systemctl start 直接 failed，
# journalctl -u grid 里只留一句 "Failed to set up output file: No such file or directory"，
# 很像代码问题，实际只是目录没建。一条命令连父目录和属主一起搞定：
install -d -o www -g www /www/log/grid

systemctl daemon-reload
systemctl enable --now grid
systemctl status grid --no-pager
```

> **在哪执行**：服务器的 shell 里，宝塔面板左下角「终端」就行；当前在哪个目录都无所谓
> （`install -d` 用的是绝对路径）。需要 root（宝塔终端默认就是 root）。
>
> 这一步对应 unit 里的 `StandardOutput=append:/www/log/grid/api.log` —— systemd
> **不会**替你把目录建出来，而且它是以 `User=www` 的身份去打开这个文件的，
> 所以目录属主必须是 www，只有 755 的 root 目录照样写不进去。

**验证**

```bash
curl -fsS http://127.0.0.1:3000/api/healthz
# 期望 {"ok":true,...,"db":"mysql:127.0.0.1:3306/grid",...}
```

看不到 `"ok":true` 就看日志：

```bash
tail -50 /www/log/grid/api.log
```

| 日志里的字样                             | 原因                                     |
| ---------------------------------- | -------------------------------------- |
| `数据库连不上`                           | `.env` 的 DB_URL 或 MySQL 账号权限           |
| `Cannot find module 'node:sqlite'` | Node 版本太低（本项目已改成懒加载，正常不会出现；出现说明跑的是旧构建） |
| `listen EADDRINUSE :3000`          | 端口被别的旧服务占了，`ss -lntp \| grep 3000`     |

## 7. nginx 站点与证书（宝塔面板，全程点界面）

### 7.1 先确认域名指向本机

```bash
ping -c1 todo.stellamp.me
# 或：dig +short todo.stellamp.me
```

要能解析到本机公网 IP。**这一步不通，后面申请证书必定失败**（Let's Encrypt 要回连 80 端口），
而且报错只会说"验证超时"，不告诉你是 DNS 还是防火墙。

云厂商的安全组也要放开 80 / 443（宝塔放行是第二道，安全组是第一道，两个都要）。

### 7.2 建站

宝塔 → 网站 → 添加站点：

| 字段 | 填什么 |
|---|---|
| 域名 | `todo.stellamp.me` |
| 根目录 | `/www/wwwroot/todo/apps/web/dist` |
| FTP / 数据库 | 都不创建 |
| PHP 版本 | **纯静态** |

> **填了 `apps/web/dist` 建站，就必须做一件事：建完立刻关掉「防跨站攻击(open_basedir)」。**
> 宝塔会往站点根目录写 `.user.ini`（`open_basedir` 配置，还可能 `chattr +i`），
> 而这个目录是 vite 的构建产物目录、每次构建都要被清空 —— 两者在一起必定打架，
> 症状见 §7.6。`open_basedir` 只对 PHP 生效，纯静态站点关掉它没有任何损失。
>
> 反过来，如果你在建站时把根目录留成了默认的 `/www/wwwroot/todo.stellamp.me`，
> 那就要多做一步 §7.4 的 `root` 修改。两条路都行，**但改完 `root` 之后
> 不要再动面板里的「网站目录」** —— 那个设置会自动重写 nginx 配置的 `root` 行。

### 7.3 先申请证书

站点 → SSL → Let's Encrypt → 勾选域名 → 申请（这一步会顺带勾上"强制 HTTPS"）。

> 如果这台机器上已有 `*.stellamp.me` 泛域名证书，直接点「其他证书」把两份 PEM 粘进去，
> 省一次申请、也少一个 90 天后续期的对象。

**先证书、后改配置**，是因为证书申请依赖站点的默认结构；先把 root 改走再申请，
出问题时很难判断是验证文件写错了位置还是别的。

### 7.4 改配置文件：两处

站点 → 设置 → 配置文件。这里有宝塔生成的完整 server 块，**不要整段替换**。

**第一处**（**只在建站时根目录留了默认的情况下需要**），把 root 指向构建产物：

```diff
-    root /www/wwwroot/todo.stellamp.me;
+    root /www/wwwroot/todo/apps/web/dist;
```

如果建站时根目录直接填的就是 `apps/web/dist`（§7.2 推荐），这一行已经是对的，跳过。

> 做完这一步之后**不要再碰面板里的「网站目录」**：那个页面保存时会重写这里的 `root`。

**第二处**，把 `deploy/nginx.conf.example` 里的【插入片段】整段粘到 `#SSL-END` 之后：

```nginx
    location ^~ /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    location ^~ /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 90s;
        client_max_body_size 2m;
    }

    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache";
    }
```

保存时面板会自动 `nginx -t`，报错会直接弹出来。

**为什么 `/assets/` 前面必须是 `^~`**：宝塔默认配置里有一条

```nginx
location ~ .*\.(js|css)?$ { expires 12h; ... }
```

nginx 的匹配顺序是「精确 `=` > `^~` 前缀 > 正则 > 普通前缀」。写成普通的
`location /assets/`，请求会先撞上那条正则，`expires 1y` 就白写了。
`^~` 的意思正是"这个前缀最长匹配时跳过正则"。

### 7.5 验证

从你自己的电脑上跑（不是服务器）：

```bash
curl -sI https://todo.stellamp.me/ | head -3          # 期望 200 + index.html 的 header
curl -s  https://todo.stellamp.me/api/healthz         # 期望 {"ok":true,...}
```

再打开浏览器访问 `https://todo.stellamp.me`，看到登录页就说明三层都通了
（nginx → 静态文件、nginx → Fastify → MySQL）。

| 现象 | 原因 |
|---|---|
| 页面 404 | root 没改，还指着 `/www/wwwroot/todo.stellamp.me` |
| 页面 200 但白屏 | `dist` 里没有 `index.html`，第 5 步的 `pnpm --filter @grid/web build` 没跑 |
| 刷新 `/habits` 变 404 | `location /` 的 `try_files` 没加，缺 SPA 回退 |
| `/api/healthz` 502 | 后端没起：`systemctl status grid` |
| 登录报 `csrf_failed` | `.env` 里的 `APP_ORIGIN` 和地址栏不一致（漏了 `https://` 或多了斜杠） |
| 登录成功但立刻掉线 | `COOKIE_SECURE=false` —— `__Host-` 前缀的 Cookie 非 Secure 会被浏览器直接丢弃 |

### 7.6 构建报 `ENOTDIR ... dist/.user.ini`

```
[plugin vite:prepare-out-dir]
Error: ENOTDIR: not a directory, scandir '/www/wwwroot/todo/apps/web/dist/.user.ini'
```

**原因**：宝塔建站时把站点根目录填成了 `apps/web/dist`，面板随即在这个目录里生成
`.user.ini`（`open_basedir` 配置）并加了 `chattr +i`。vite 每次构建前要清空
`outDir`，删到这个文件时按目录递归，于是 `ENOTDIR` 直接中断构建。

**立即修复**：

```bash
chattr -i /www/wwwroot/todo/apps/web/dist/.user.ini 2>/dev/null || true
rm -rf /www/wwwroot/todo/apps/web/dist/.user.ini
```

`deploy.sh` 的第 4 步已经内置了这段清理，所以脚本重跑不会卡住。

**根治**：宝塔 → 网站 → 站点设置 → **网站目录** → 把「防跨站攻击(open_basedir)」关掉 → 保存。
关闭时面板会自动删除 `.user.ini`，之后不再生成。纯静态站点用不到它，它只对 PHP 生效。

> ⚠️ **不要用「改网站目录」来解决这个问题。** 那个设置会连带重写 nginx 配置里的
> `root` 指令 —— 你把根目录改回默认，`root` 也跟着回到默认，页面直接 404。
> 要动就动「防跨站攻击」这一项，别动目录路径。
>
> 判断依据：如果 `apps/web/dist` 里出现 `.user.ini`、`404.html`、宝塔的默认首页，
> 说明站点根目录指着构建产物，且防跨站攻击是开着的。

## 10. 备份与监控

数据的风险不是一个，是三个层次，对应的手段也不一样：

| 风险 | 场景 | 靠什么挡 |
| --- | --- | --- |
| 误删 / 改错 | 手滑删了一个清单，或者规则写错把一批任务的状态搞乱 | 本机 14 天备份，可回到 6 小时前的任一时刻 |
| 服务/磁盘故障 | ECS 磁盘挂了，或者重装系统把 `/www` 覆盖了 | **备份必须在另一台机器上**——本机备份跟数据库同盘，会一起没 |
| 人为灾难 | 库被 DROP，或账号被盗后清库 | 只有「另一台机器 + 定期导出」这一条路 |

本机备份和异地备份是两件事，**两个都要做**。

### 10.1 服务器自动备份（每 6 小时）

宝塔 → 计划任务 → 添加任务：任务类型「Shell 脚本」，执行周期「N 小时」= 6，脚本内容：

```bash
bash /www/wwwroot/todo/deploy/backup.sh
```

对应 cron：`0 */6 * * *`。

为什么不是常见的「每天 02:00 一次」：如果下午三点误删数据，等到第二天凌晨才备份，
那时删除状态已经写进库里了，你只能回到「已经被删掉」的那一刻。6 小时粒度最坏丢半天，
代价只是多占几 MB。

脚本会自动判断驱动（`DB_URL` 以 `sqlite:` 还是 `mysql://` 开头），你不用管。

保留策略：

- `daily/` 保留 14 天（每 6 小时一份，最多 56 份）
- `weekly/` 每周日另存一份，保留 8 份（约两个月）
- 日志里会写清本次结果和当前份数

每次备份都会做两道校验，避免留下「看起来正常」的半个文件：

1. `gzip -t` 确认压缩流完整
2. 确认 dump 末尾有 mysqldump 的 `-- Dump completed` 结束标记

只检查文件大小是不够的：连接在传输中途被断开时，前面几十 MB 照样已经落盘了。

**如果备份失败**，脚本会把原因写进 `/www/backup/grid/status.txt`（首字段为 `FAILED`），
`healthcheck.sh` 读这个文件报警。想让它主动通知你，在 `.env` 里加一行通用 webhook：

```bash
BACKUP_WEBHOOK_URL=https://oapi.dingtalk.com/robot/send?access_token=xxx
```

钉钉、飞书、自建接口都吃同一种 `{"msgtype":"text","text":{"content":"..."}}` 格式。
不配就静默跳过，不影响备份本身。

### 10.2 异地：把备份拉到你自己电脑（推荐，无需对象存储）

这是整套方案里**唯一能扛住「服务器整个没了」**的一环。没有 OSS 完全不影响，
用你手上的 Windows 电脑就行。

首次配置（只做一次）：

```powershell
# 1) 确认本机有 OpenSSH 客户端
ssh -V

# 2) 生成密钥，并把它加到服务器（之后就不用输密码了）
ssh-keygen -t ed25519
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh root@todo.stellamp.me "mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys"

# 3) 验证
ssh root@todo.stellamp.me "echo ok"
```

然后手动跑一次：

```powershell
powershell -ExecutionPolicy Bypass -File "E:\11_WorkBuddyFiles\Todo\tools\pull-backup.ps1"
```

默认行为：连 `todo.stellamp.me`，把最新 3 个备份拉到 `%USERPROFILE%\GridBackup`，
本地保留 40 份，跳过已经存在的同名文件，并校验下载到的确实是 gzip 文件。

改成每天自动跑：任务计划程序 → 创建基本任务 → 每天 21:00 → 启动程序：

```
程序：powershell.exe
参数：-ExecutionPolicy Bypass -File "E:\11_WorkBuddyFiles\Todo\tools\pull-backup.ps1"
```

脚本只读不删，服务器上的东西它一份都不会动。

> 如果你后来搞到了对象存储（阿里云 OSS / 腾讯云 COS / Cloudflare R2 都行），
> 用 `rclone config` 建一个名字叫 `oss` 的 remote，`backup.sh` 会自动把新备份传上去。
> 那是多一层保险，但**不能替代**本地拉取——同一个云账号下的两份东西，
> 账号欠费或被盗时会一起消失。

### 10.3 用户侧导出（最后一道保险）

即使上面两层全失效，你手上还有一份 JSON。

- Web：设置 → 备份与导出 → 「导出全部数据（JSON）」
- 手机：设置 → 数据备份 → 「在浏览器里导出」（手机上存不住文件，一律在网页版做）

导出内容包含待办、标签、清单、重复例外、日程、打卡记录与冲突历史，**包括已删除的行**
（墓碑），这样恢复时才不会出现「父任务回来了、子任务没了」。
接口是 `GET /api/export`，需登录；`GET /api/export/stats` 只返回各表条数。

这个文件里是你的完整隐私副本（日历、打卡、备注都在里面），别放到公开的地方。
建议每次大改动前导一份，丢进网盘或移动硬盘。

### 10.4 监控

```bash
bash /www/wwwroot/todo/deploy/healthcheck.sh
```

退出码：`0` 正常 / `1` 服务异常 / `2` 服务正常但备份异常（失败或超过 14 小时没成功过）。

`rssMB > 300` 只告警不算失败——那是判断 2C2G 撑不撑得住的信号，不是故障。

挂到宝塔「网站监控」或 Uptime Kuma，每 5 分钟一次。别只看 HTTP 200：
**备份挂掉是完全静默的**，探活是唯一能发现它的地方。

### 10.5 恢复

```bash
bash /www/wwwroot/todo/deploy/restore.sh /www/backup/grid/daily/grid_2026-11-24_0200.sql.gz
```

不带参数运行会列出最近的 10 份备份。

脚本的顺序是刻意的：

1. 先把**当前**的库导一份到 `pre-restore/`——恢复错文件时你还能回去
2. 停服务 → 灌数据 → 起服务。必须先停：一边有业务写、一边 `DROP TABLE` 重建，
   结果是一半旧数据一半新数据，而且不会报任何错
3. 探活，确认服务真的能读回来

需要手动输入 `yes` 才会执行。回滚就是把 `pre-restore/` 里那份再跑一遍。

### 10.6 恢复演练（别等真出事才第一次用）

没验证过的备份不算备份。搭好之后一周内至少走一遍：

1. 在服务器上另建一个空库 `grid_drill`
2. 把最新的备份灌进去：
   ```bash
   gunzip -dc /www/backup/grid/daily/grid_YYYY-MM-DD_HHMM.sql.gz | mysql -ugrid_rw -p grid_drill
   ```
3. 查行数对不对：
   ```sql
   SELECT COUNT(*) FROM task;
   SELECT COUNT(*) FROM habit_log;
   ```
   和服务端 `/api/export/stats` 显示的数字对一下
4. 确认最后一个表也导全了（dump 末尾有 `-- Dump completed`）
5. 演练库用完就删掉

每半年重做一次。中途换过服务器、改过 `.env`、升级过 MySQL 之后都要重做——
这几件事都会让「备份能恢复」这个假设失效。

## 11. 故障对照表

| 现象                 | 定位                                                 | 处理                                                                                                    |
| ------------------ | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 页面能开，登录后立刻跳回登录页    | DevTools → Application → Cookies 里没有 `__Host-grid` | `COOKIE_SECURE=true` 且 HTTPS 生效；`APP_ORIGIN` 必须与地址栏完全一致                                               |
| 登录报 `页面状态已过期`      | 403 `csrf_failed`                                  | `APP_ORIGIN` 不一致，或经过了一层没透传 `Origin` 的代理                                                               |
| 日历一直「同步中」不动        | `tail /www/log/grid/api.log`                       | 令牌过期 → 设置页会显示红色通栏「需要重新授权」，点它重连                                                                        |
| 授权后报 `AADSTS50011` | Azure 重定向 URI                                      | 与 `.env` 的 `MS_REDIRECT_URI` 逐字符对齐（结尾不要加 `/`）                                                         |
| 服务起来又马上退出          | `systemctl status grid`                            | 多半是 `WorkingDirectory` 或 `EnvironmentFile` 路径不对；也可手动 `cd packages/server && node dist/index.js` 看真实报错 |
| `journalctl -u grid` 只有一句 `Failed to set up output file` | 日志目录 | 第 6 节那条 `install -d -o www -g www /www/log/grid` 没执行，或目录属主不是 www |
| `failed because of unavailable resources` / `Failed with result 'resources'` | 看 journal 的上一行 | 这是个垃圾桶类别，`EnvironmentFile`/`WorkingDirectory` 缺失都归它。按 6.1 的对照表逐条对，别去调 `MemoryMax` |
| `Failed to load environment files: No such file or directory` | `.env` | 第 4 步的 `cp deploy/env.example .env` 没做，或 `EnvironmentFile` 路径不对（最常见） |
| 每次部署后都要重新登录        | Cookie 名或 `TOKEN_ENC_KEY` 变了                       | `TOKEN_ENC_KEY` 一旦上线就不要动                                                                              |
| 内存缓慢上涨             | `curl /api/healthz` 的 `rssMB`                      | > 300 重启一次；持续上涨再查                                                                                     |

## 附：和现有站点的关系

这台机器上同时跑着 yalta / holmes / gcx-api。本项目的边界：

- 后端只监听 `127.0.0.1:3000`，不占公网端口
- 数据库用**同一个 MySQL 实例**里的独立库 `grid` + 独立账号 `grid_rw`（不碰别人的库）
- 静态文件在 `apps/web/dist`，由 nginx 直接发，不经过 Node
- 备份目录 `/www/backup/grid`，与其它项目的备份互不覆盖

唯一共享的资源是 MySQL 实例和 nginx。所以**不要**为了这个项目去改全局的  
`innodb_buffer_pool_size`（1 GB 机器上它已经在被三个站点分）。
