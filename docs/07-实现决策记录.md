## ADR-001 数据库访问层：不用 Drizzle，改「薄 SQL 层 + 双驱动」

**状态**：已采用（M0）

**文档原文**：docs/02 §2 选型表写的是「ORM: Drizzle，理由：类型安全、迁移可读、SQL 可控」；§4 目录里是 `src/db/{schema.ts, migrations/0001_init.sql}`。

**实际情况**：`packages/server/src/db/` 下是一个 60 行的 `Db` 接口 + 两个驱动实现（`sqlite.ts` / `mysql.ts`），SQL 写在调用处，迁移是手写 `.sql` 文件 + 40 行 runner 与 40 行语句切分器。

**为什么改**

1. **本地开发必须零安装。** 你的机器上没有 MySQL、没有 Docker。如果只支持 MySQL，`pnpm dev` 第一天就跑不起来，而「跑不起来」会一路卡到 M6。
2. **Drizzle 的 schema 是方言绑定的。** 要同时支持 SQLite 与 MySQL，就得写两份表定义，而两份表定义必然漂移 —— 偏偏漂移会发生在 M2 的同步表上，那里出错是数据错乱，不是报错。
3. **本项目查询量极小**（单用户，全表加起来几千行，总共约 50 条 SQL）。ORM 的类型推导收益，抵不过方言分叉的成本。

**代价（明写）**

- 没有 ORM 的类型推导：行类型要手写 `interface` 并依赖调用方自律。缓解：所有跨层返回都过 zod（`packages/core` 的模型），边界上有校验。
- 复杂查询（M7 的统计报表）要手写 SQL。对 2C2G 与「能看懂执行计划」这个诉求来说，这反而是优点。
- 迁移没有 `drizzle-kit generate`，改表要自己写 SQL。缓解：迁移只增不改，且每个文件顶部写清目的。

**约束（写进 README 与 03 文档）**：SQL 只用可移植子集 —— `?` 占位符、不用 `ON DUPLICATE KEY` / `ON CONFLICT`、不用窗口函数 / CTE / JSON 函数、布尔存 0/1。

## ADR-002 时间字段：`DATETIME(3)` → `BIGINT`（epoch 毫秒）

**状态**：已采用（M0）

**文档原文**：docs/03 的 DDL 用 `DATETIME(3)`；docs/02 §3.2 里 MySQL 设 `default-time-zone = '+08:00'`。

**实际情况**：所有时间字段都是 `BIGINT`，存 epoch 毫秒（UTC 绝对时间），`node:sqlite` 与 `mysql2` 都按普通整数处理。MySQL 连接的 `timezone` 显式设为 `'Z'`。

**为什么改**

1. **跨方言零歧义**：SQLite 没有 DATETIME 类型，只有 TEXT/INTEGER 亲和性；同一份 DDL 无法在两边表达同一语义。
2. **跨时区零歧义**：服务器时区、浏览器时区、用户出差改时区，三者任一变化都可能让「日期」漂移一天。存绝对时间戳后，展示层用 `date-fns-tz` 按用户时区渲染，语义唯一。
3. **M2 需要它**：冲突解决要用 HLC（混合逻辑时钟），HLC 的物理分量本来就是毫秒时间戳，存 DATETIME 还得来回转。

**代价**：写 SQL 时不能再用 `DATE_FORMAT` / `date BETWEEN` 这类人类可读写法，要看时间得 `datetime(created_at/1000,'unixepoch','+8 hours')`。运维查库时麻烦一点。

## ADR-003 迁移文件放在 `packages/server/migrations/`（不在 `src/` 下）

**状态**：已采用（M0）

**原因**：`tsc` 只编译 `.ts`，不会把 `.sql` 复制进 `dist/`。放在 `src/` 下就必须再加一步 `copy-assets` 脚本，而这类脚本最容易在「本地正常、服务器缺文件」时出事。放在包根目录，dev 与 prod 走同一条解析路径（`paths.ts` 里的 `serverRoot`）。

## ADR-004 会话 Cookie 名：开发 `grid_s`，生产 `__Host-grid_s`

**状态**：已采用（M0）

**文档原文**：docs/02 §5.2 写死 `__Host-grid_s`。

**为什么改**：`__Host-` 前缀强制要求 `Secure`，而本地 `http://localhost` 上带 `Secure` 的 Cookie 在部分浏览器/版本会被直接丢弃。这种失败的表现是「登录成功但刷新就掉线」，极难排查。

**实现**：`env.cookieSecure` 决定名字与属性；生产环境启动时强制校验 `COOKIE_SECURE=true`，否则直接退出（宁愿起不来，也不要静默降级成不安全 Cookie）。

**文档原文**：docs/02 §11 的部署步骤里单独跑 `pnpm --filter server db:migrate`。

## ADR-008 OAuth 令牌加密：自研 60 行 AES-256-GCM，不引第三方库

**状态**：已实施（`packages/server/src/oauth/token-cipher.ts`）

**选择**：`node:crypto` 的 `createCipheriv('aes-256-gcm')`，存储格式 `v1.<iv>.<tag>.<ct>`（四段 base64url）。

**为什么不用 `crypto-js` / `jose` / KMS SDK**：

1. GCM 自带完整性校验，密文被改一个字节解密就抛错——这比「静默返回乱码再去请求微软」重要得多。
2. 带 `v1.` 版本前缀，以后换密钥或换算法可以按前缀分派，不需要停机重写全部数据。
3. 引入库只省 60 行，却多一个供应链依赖；而这段代码的测试成本很低（加密→解密往返 + 篡改一字节必须失败）。

**约束**：`decrypt` 失败必须抛错，绝不返回空串。返回空串会把「密钥换了」误诊成「用户需重新授权」。

## ADR-009 `oauth_state` 只存 SHA-256，且一次性消费

**状态**：已实施

与 `session` 表同一套纪律：库里只有 `sha256Hex(state)`，没有明文 state。

**回调顺序踩过一次坑**（已修）：最初把「微软返回 error」的分支放在 `consumeState` 之前，结果用户点「取消」后那条 state 会一直留到 10 分钟过期。现在改成**先消费 state 再判断 error** —— 微软无论成功还是拒绝都会原样带回 state，所以这个顺序才是对的。

**验证结果**：同一 state 第二次请求返回 `state_invalid`；伪造 state 返回 `state_invalid`；不带 state 返回 `missing_params`。

## ADR-010 `redirect_uri` 由 `APP_ORIGIN` 推导，而不是必填

**状态**：已实施

`MS_REDIRECT_URI` 留空时自动取 `${APP_ORIGIN}/api/oauth/microsoft/callback`。

**原因**：这个值必须与 Azure 注册值逐字符一致，是最高频的 `AADSTS50011` 来源。让它由 `APP_ORIGIN` 推导，开发者只需要维护一处；本地（`http://localhost:5173/...` 经 Vite 代理到 3000）与生产（`https://todo.stellamp.me/...` 经 nginx 转发）走的是同一条路径，不会出现「本地能连、线上报 50011」。

**代价**：如果将来把回调放到独立子域，必须显式写 `MS_REDIRECT_URI`。

## ADR-011 Graph 调用失败必须翻译成业务错误（实测发现的缺陷）

**状态**：已实施

**现象**：用假 access token 点「验证令牌」，前端显示「服务端异常，请查看服务日志」（HTTP 500）。

**原因**：`fetchMe` 抛的是 `GraphError`，路由没捕获，落到全局错误处理器当成未知异常。

**修法**：加 `callGraph()` 包装，把 Graph 状态码映射成：

| Graph 返回 | 对外 | 前端表现 |
|---|---|---|
| 401 / 403 | `409 reauth_required` + 标记 `needs_reauth` | 提示「请重新连接 Outlook」，状态胶囊变黄 |
| 429 | `503 graph_rate_limited` + `Retry-After` | 提示限流并给出等待秒数 |
| 0（连不上） | `504 graph_unreachable` | 提示检查出站网络 |
| 其他 4xx/5xx | `502 graph_error` | 带 graph code，便于对照微软文档 |

**为什么这条重要**：令牌失效是用户最常遇到的故障。显示「服务端异常」会让人以为是自家后端的 bug，而正确动作只是点一次「重新授权」。

## ADR-012 OAuth 配置：全空则关闭，半配置则拒绝启动

**状态**：已实施

| 配置情况 | 行为 |
|---|---|
| 三项全空 | 正常启动，`/api/oauth/*` 返回 503，前端显示「未配置」与四步指引 |
| 三项齐全 | 正常启用 |

## ADR-013 M1 的 `quadrant` 是"存了但不作真源"的派生字段

**决策**：客户端同时存 `important` / `urgent`（真源）与 `quadrant`（派生），所有写入统一走 `repo`，由 `quadrantOf()` 重算。

**原因**：四象限是最高频查询，需要 `quadrant` 能被 IndexedDB 索引（服务端用 `GENERATED STORED` 列，是同一个道理）；但两个布尔才是语义源头，`quadrant` 只是 `4 - (important*2 + urgent)` 的编码。

**风险点**：如果哪天有人在组件里直接 `db.tasks.put({...task, quadrant: 3})` 而不改布尔，两套值就会漂。因此视图层**不允许 import `db`**，只能 import `repo`——这条纪律是 ADR 的核心，不是风格偏好。

## ADR-014 行高写死 48px，换来 3000 条不掉帧

**决策**：`VirtualList` 只渲染可视区 + 8 行缓冲，行高恒为 `--row-h`（48px），行内禁止换行、禁止折叠成两行。

**实测**：3000 条任务（4 列各 750）时首屏可用 427ms、DOM 里只有 92 行、滚动帧时间 p50 6.1ms / p95 7.6ms（60fps 预算 16.7ms）。

**代价**：行内信息只能放一层（标题 + 时间 + 标签），备注必须去抽屉里看。这是刻意的取舍——列表是扫描用的，不是阅读用的。

**如果以后要"两行行高"**：把 `rowHeight` 改成传入不同值即可，但同一列内必须统一，否则位置计算会错。

## ADR-015 删除 = 软删 + 5 秒物理删除，而不是"确认弹窗"

**决策**：单条删除立刻软删（`deletedAt`），底部出撤销条 5 秒；窗口结束才 `bulkDelete`。启动时 `purgeExpired(10s)` 补刀。

**原因**：需求写的是「二次确认**或**撤销机制」。对高频操作来说，撤销比确认好——确认框会训练用户无脑点确定，撤销则真的能救回来。

**已接受的边界**：撤销只保留**最后一条**。连续删两条时，第一条立即落地。这是为了不骗用户（否则他会以为能连撤多步）。

## ADR-016 完成父任务 = 完成整棵子树

**决策**：`toggleComplete` 沿物化路径把整棵子树一起改状态。

**原因**：只改父级会留下"父任务已完成、子任务还开着"的鬼状态，在四象限里看起来像 bug。

**已知不足**：取消完成时会把子任务里**原本就已完成**的也一起改回未完成。M3 引入 `rev` 级别的撤销栈后修；当前单用户场景影响很小。

## ADR-017 重复规则是**一个字符串**，不拆成 until/count 三列

**决策**：`task.rrule` 存完整 iCal 规则（含 `UNTIL=` / `COUNT=`），不实现 docs/03 §4.3 里的 `rrule_until` / `rrule_count` 两个独立列。

**原因**：文档 §6 已经把"重复规则"定义为**原子块**——整块二选一，不拆字段。既然合并时按整块走，落库时再拆成三列就是自找麻烦：`FREQ` 与 `UNTIL` 分别被两台设备改过时，服务端会拼出一条**谁也没写过**的规则（例如"每两周"配上了另一条规则的最后日期）。

**代价**：Graph 映射时要现场解析出 range（M4 做）。解析失败会抛错，不会静默降级。

## ADR-018 例外独立成表，且**墓碑不物理删除**

**决策**：`recur_exception` 是独立实体，参与同步；删除只写 `deleted_at`，不删行。

**原因**：例外要单独增量、单独记冲突、单独软删（docs/03 §4.4）。塞进 `task.exdate` JSON 列的话，改一次例外就抬高母体 `rev`，两端看到"整行变了"，字段级合并无法判断改了哪里，于是次次报假冲突。

**墓碑必须保留**的原因在唯一键：`UNIQUE (series_id, original_start)`。同一次"先删掉、后改回来"如果新建一行会撞唯一索引被服务端拒绝。所以客户端 `upsertException` 会复用（复活）已有行而不是插入新行。

**推论**：服务端 `merge` 对 `kind` 单独判定"删除优先"——同一次同时被标删除与改写时，删除赢。保留一条被改写的会议比少一条会议更容易造成事故。

## ADR-019 "本次及后续"的截断点是**上一个真实实例**

**决策**：拆分系列时，母体的新规则用 `UNTIL = 上一个真实发生过的开始时间`，不是 `cutoff - 1 天`。

**原因**：规则可能是"每周一三五"，cutoff 落在周二。用"减一天"会把周一那次也砍掉。用"上一个实例"则无论规则多稀疏都准确。

**顺序要求**：先截断母体、再建新系列、再改挂例外、最后（仅当 cutoff 是第一次时）删母体。反过来做会瞬时出现"两条系列都有周五"的重复块，或"例外指向已删母体"的孤儿。

## ADR-020 令牌只存一份：oauth_account 加列，不新建 calendar_account

**决策**：文档 03 §4.6 的 `calendar_account` 不落地；令牌继续用 M0b 的 `oauth_account`，只给它加 `delta_link_* / last_sync_at / window_*` 几列。

**原因**：同一份 refresh token 存在两张表里，迟早会出现"一张表刷新了、另一张还是旧值"，而微软**轮换** refresh token——用旧值再刷一次就是 `invalid_grant`，症状是"授权莫名其妙失效"。数据库层面能消除的歧义不要留给代码去维护。

**代价**：`calendar_account` 这个名字在文档里仍然存在，读文档的人需要知道它被合并了。

## ADR-021 只用一个 delta 通道，而且**按日历**拉

**决策**：`GET /me/calendars/{id}/events/delta`，每个 `calendar_source` 各存一条游标。

**三个被实测否掉的方案**：

| 方案 | 否决原因 |
|---|---|
| `/me/events/delta` 一把抓 | 事件对象里**没有** `calendarId`；`$select=parentFolderId` 直接被 Graph 拒绝（`Could not find a property named 'parentFolderId'`）。拿不到归属日历，"节假日不同步""只读日历不能拖"就实现不了 |
| `calendarView/delta`（文档 §6.4 的主通道） | 它把重复事件**展开成实例**返回，每个实例一个 id，窗口一滑动就"新增一堆、消失一堆"。照它写库等于把"规则 + 例外"退化成一堆快照，本地再也无法用 RRULE 展开，翻到下个月就是空的 |
| 两条通道都写 `cal_event` | 两条通道给的 id 语义不同（实例 id vs 母体 id），会互相把对方的行删掉 |

**顺带一条硬约束**：delta 端点**不接受 `$top`**（会报 `ErrorInvalidUrlQuery`，因为分页边界无法保证），页大小只能用 `Prefer: odata.maxpagesize`。文档 §6.4 没写这条，踩过一次。

## ADR-022 P0 不镜像 `type=exception` 的单次改写

**决策**：重复事件的母体（seriesMaster）照常镜像并按 RRULE 展开；`type=exception` 的实例整条跳过。

**原因**：例外要正确显示，需要给 `recur_exception` 加 `series_kind` 并让合并逻辑区分"任务的例外"和"Outlook 的例外"，这是 P1 的工作量。P0 已明确"重复事件只读"，而**少显示一次改写**与"显示在错误日期上"相比，前者是缺功能、后者是给错信息。

**代价**：用户在 Outlook 里单独挪动某次例会，GRID 上仍显示原时间。这条已写进 06 验收清单的"已知偏差"。

## ADR-023 单个日历失败**不能**拖垮整次同步

**原因**（真实踩到）：清理测试日历时，那个源的 delta 游标变成永久 404。`pullEvents` 原本按源循环且不捕获异常，于是**第一本坏日历就让后面所有日历都拉不到**，而日志里只有一行 404。

**做法**：
1. 每个源 `try/catch`，失败只记 firstError；只有"全部源都失败"才上抛（让 UI 的 `last_error` 有东西可显示）。
2. 401/403 例外——那是授权问题，必须立刻上抛，让界面出红色通栏。
3. 404/`ErrorItemNotFound` 判为"日历已删"：`retireSource()` 把源和它的事件一起打墓碑。

**推论**：`syncSources` 发现 Graph 上少了某个日历时也走 `retireSource`。只软删源是不够的——事件行还活着，但源已经被过滤掉，再没有任何一次 pull 会碰到它们，那些会议就永久挂在日历上。

## ADR-024 打卡记录的主键是 `hash(habitId + logDate)`，不是 ULID

**原因**：这是全项目唯一一个**必须**确定性的主键。

```
设备 A 今天点"喝水 +1" → op-create(id=X, value=3)
设备 B 今天也点"喝水 +1" → op-create(id=Y, value=5)
```

随机 id 时两条都是"新行"，服务端各插一条，界面上 3 + 5 变成 8/8 —— 用户看到的是打卡翻倍，
而且**没有任何后续操作能纠正**：本地已经是两条了，下一次同步只是把它俩再确认一遍。

确定性 id 之后，B 的 op 命中的是同一行，于是走"同一条记录的字段级合并"，取较大值。

**做法**：
1. `habitLogId(habitId, logDate)` 用 Crockford base32 编码，26 字符（服务端列是 `VARCHAR(26)`），前 6 位是日序号，其余是四路哈希。
2. 服务端 `checkLogIdentity` 校验 `id === habitLogId(habitId, logDate)`，不符直接 `rejected: nondeterministic_log_id`。**不做兼容**：放过一次就等于允许"同一天两行"这个 bug 永久存在。
3. 表上再加 `UNIQUE (habit_id, log_date)` 兜底——应用层算错时宁可这次写入失败，也不能在库里留下脏数据。

## ADR-025 打卡数值合并取 `GREATEST`，且规则必须放在 `remoteUnchanged` **之前**

**原因**：两台设备同一天各点一次，真值取较大者；相加会得到"今天已经喝够了"的假象。

**但只有"取 max"还不够**，位置也关键。`merge.ts` 的第一道判断是：

```
current[field] === base[field]  → 远端没动过，直接采用 incoming
```

而"两台设备离线时各自 create 了同一天的同一条记录"这个最常见场景，恰好满足它：
第二台的 op 到达时服务端已有行、`base` 是空的 → `remoteUnchanged` 成立 → 直接采用第二台的值。
于是会出现"先打到 5，被离线设备覆盖成 3"，**数字反而变小**，而且没有任何提示。

所以 habit_log 的 `value` 与 `backfilled` 两个分支放在 `remoteUnchanged` 之前，
和四象限整体裁决同一个层级：它们的语义是"与时钟无关的合并规则"。

**`backfilled` 用 AND**（真打卡优先）：同一行一边是当天记的、一边是补记的，取"当天记的"。
反过来会把真的那天染成空心环，用户会以为自己记错了。

## ADR-026 统计全部是纯函数现算，**不存任何累加列**

**原因**：`streak` / 完成率 / 热力图都只吃一个输入——"达标日期集合"。
一旦为了性能缓存 `current_streak` 之类的列，就同时欠下四笔债：
删记录要回退、改目标要重算、跨时区要重算、补卡要重算。
漏掉任何一笔的症状都是"删了记录但连续天数不变"，而用户会认为数据没删掉。

3000 个记录（约 8 年单习惯）的全量重算在浏览器里是亚毫秒级，没必要缓存。

**推论（M5 出口条件就是这四条）**：
1. 今天还没打卡不算断——否则每天凌晨所有人都会看到"连续天数归零"。
2. 跨月/跨年靠"日序号"加减，不看月份长度表，闰年 2 月 29 与 3 月 1 自然相邻。
3. 时区只影响"今天是哪天"，不影响任何算术（`YYYY-MM-DD` 字符串 + UTC 日序号）。
4. 删除记录后重算即回退，因为没有任何累加字段。

## ADR-027 补卡必须**看得见**（空心环），而不是默默算作达标

**原因**：一次补记 10 天和真的坚持 10 天，在数据上完全等价（都是 10 条达标记录）。
如果视觉上也等价，热力图就从"如实反映"退化成"用户想让它是什么样就是什么样"，
而这个功能的价值恰恰在于它不撒谎。

**做法**：`setLog` 只要 `logDate < today` 就置 `backfilled: true`；热力图上画成空心环
（用 `outline` 而不是斜纹——设计规范禁止渐变，且 14px 的格子上斜纹认不出来）。
连续天数与完成率**照常算它达标**：它是真实发生的事，只是不是当天记的。

## ADR-028 `/api/habits/summary` 是只读专用接口，写入一律走 `/sync/push`

**原因**：打卡的读放大比别的表都高——一个习惯一年 365 行。手机端的小组件、每日提醒
每次醒来全量 pull 一遍是白烧流量和电。而它们要的数据形状是固定的"习惯 + 最近 N 天记录"。

**纪律**：这个接口**只读**。若允许它写，就会出现两条写路径各自维护合并规则，
而两条路径的语义迟早分叉——比如这边忘了取 max，打卡数字就开始相加。

**日期由客户端给**（`?today=YYYY-MM-DD`）：服务端经常跑在 UTC 机器上，
让它自己算"今天"会在跨零点前后差一天，症状是"晚上 11 点打的卡显示在明天"。
